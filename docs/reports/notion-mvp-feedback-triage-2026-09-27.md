# Notion MVP·내부테스트 2 대조

확인일: 2026-09-27

## 결론

**최신 Notion MVP가 제품 범위의 기준이고 내부 테스트는 결함·사용성 개선의 참고 자료다.** 테스트 화면의 순번·기능 제안이 MVP와 충돌하면 MVP를 유지한다. 이번에는 문서와 이슈만 정리했으며 앱·서버 코드, 운영 설정과 데이터는 변경하지 않았다.

## 확인 범위

로그인된 Notion 브라우저에서 다음 문서를 읽었다. 공개 저장소에는 비공개 URL·페이지 ID·원본 캡처·계정·개인정보를 옮기지 않는다.

- `최소 MVP 개발 명세서`
- `보들 MVP 개발 명세서 | 개발팀 통합본 v1.1`
- `보들 MVP 화면별 상세 개발 명세서 v2.2`의 전체 흐름·요약표
- `개발 정책 관련 내용`
- `내부 테스트 및 피드백(보들 앱 화면 피드백)`의 본문·캡처·추가 메모

저장소 기준은 `master`의 `0cee66224db123251da10c5508e13543e5926760`이다. 관련 이슈와 PR 상태를 GitHub에서 다시 확인했다. Figma 원본·법률 원본·관리자 웹 전체·운영 가용성·실기기·외부 공급자는 이번에 새로 검증하지 않았다.

9월 21일 문서와 9월 26일 일부 이슈의 `내부테스트 2 제목만 있음` 설명은 당시 관찰 기록이다. 9월 27일에는 실제 항목과 캡처가 있어 현재 기준 문서·이슈를 갱신했다. 9월 27일은 대조일이며 테스트 실시일로 추정하지 않는다.

## 판단 근거

- 작업 목적: 최신 MVP를 유지하면서 내부 테스트에서 드러난 문제를 누락 없이 작업 단위로 연결한다.
- 선택한 방식: 기존 #420·#422·#423·#424는 범위·완료 기준을 보완하고, 중복되지 않는 가독성·하단 메뉴 문제만 새 이슈로 만든다.
- 대안: 피드백의 모든 문구를 요구사항으로 채택하거나 옛 7단계 화면에 맞춰 전체 구조를 바꾸는 방식은 최신 MVP·권한·진행 이력을 훼손할 수 있다.
- 선택 이유: 현재 MVP 규모에서는 가독성·화면 이동을 작은 수정으로 확인하고 외부 공급자·지도 재설계와 분리하는 편이 검증 부담이 적다.
- 리스크: 캡처의 빌드·세션 정보 부재로 이미 바뀐 화면을 다시 수정하거나 팀원의 열린 PR과 충돌할 수 있다. 착수 전에 기준 SHA와 실제 `stepCode`를 확인한다.

## 검증과 남은 범위

- Notion 본문·캡처 확인과 GitHub 이슈·PR 상태 대조를 수행했다. 앱 동작을 재현하거나 서버·DB·계정 권한을 변경하지 않았다.
- 문서 7개의 UTF-8·비공개 참조 제외 검사, 로컬 Markdown 링크 432개와 `git diff --check`를 통과했다. 기존 제목 앵커는 변경하지 않았으며 문서 전용 변경으로 Android·Core 빌드는 실행하지 않았다.
- GitHub 변경은 개인 개발 계정으로 수행했다. Project 필드 권한이 없는 현재 CLI로는 백로그 연결·필드 변경을 완료하지 못했으며, 신규 이슈 본문에 권장 우선순위를 명시했다.
- 기기·에뮬레이터·공급자 호출과 지도 확정은 이번 범위에 없다. 실제 구현 착수 시 [내부 테스트 가이드](../operations/internal-test-guide.md)의 재현 조건을 사용한다.
- 관련 문서는 [기준 체계](../planning/source-of-truth.md), [MVP 범위](../planning/mvp-scope.md), [제품 정합성](../planning/notion-product-alignment.md), [구현 상태](../status/implementation-status.md)다.
