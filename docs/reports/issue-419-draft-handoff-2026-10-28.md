# 보호자 예약 원문 전달 서버 검증

## 구현한 내용

- 보호자가 정규화된 예약 원문을 지정 환자에게 보내고 두 당사자가 같은 원문을 다시 조회하는 API를 준비했다. 최신 활성 50건 목록에는 식별자·시각만 포함한다.
- 리뷰 후 목록 참여자 검증을 요청 단위로 묶었다. 사용자·Firebase UID의 중복 조회를 없애고, 외부 조회 중 DB 트랜잭션을 유지하지 않는다. 비활성·누락도 해당 요청 안에서만 재사용하고 외부 오류는 503으로 전달한다.
- 저장된 원문을 기준으로 환자 승인과 보호자 접수를 호출한다. 클라이언트가 승인·접수 시 다른 원문으로 바꿀 수 없으며, 기존 승인 행 잠금·최소 접수증·정보공유 분리를 유지한다.
- 현재 프로필의 이름과 마스킹 전화번호를 표시한다. 다른 사용자 검색, 일반 연락처 공개, 실명 인증은 추가하지 않는다.
- 같은 보호자·요청 ID는 불변이다. 재시도가 만료를 연장하지 않으며 동시 저장에서도 보호자별 활성 20건 한도를 유지한다.
- 최대 24시간·예약 시각 전 조회 만료, 만료 원문 파기용 건수 조회·배치 함수, 계정 삭제 영향도와 안전 rollback을 V26 소스로 준비했다. 원문을 파기해도 요청 키·참여자·해시·시각은 남겨 ID 재사용을 막는다.

## 변경된 범위

Core API의 초안 Repository·Service·Controller, V26과 rollback, 격리 PostgreSQL 검증, 삭제 영향도 집계 및 관련 문서다. Android 소스와 관리자 웹은 수정하지 않았다. 기존 원문 직접 전달 API는 호환성을 유지한다.

관리자 웹·Data API에는 원문 테이블 권한을 부여하지 않는다. 새 테이블에서 Core runtime은 읽기·삽입만 가능하고 UPDATE·DELETE·파기 함수 실행은 불가능하다. 파기 role은 원문 직접 조회 없이 제한된 함수만 실행한다.

## 검증

- 로컬 JDK 21 `core-api check`: 리뷰 수정 후 596건 통과, 실패·오류·건너뜀 0건. 최초 구현의 583건에 목록 검증 회귀 검사 13건을 추가했다.
- 권한·feature OFF·만료·멱등성·한도·원문 fingerprint·입력 타입·no-store·접수증 복구·삭제 영향도 회귀 검사를 포함한다.
- 리뷰 후 동일 참여자의 반복 초안·다른 쌍의 공유 참여자·비활성/누락·다음 요청 재조회·외부 오류·기존 트랜잭션 진입 거부 검사를 추가했다. 격리 PostgreSQL 검사는 실제 Spring proxy와 JDBC 조회 후 외부 호출 시 트랜잭션·DataSource 자원 바인딩이 없는지도 확인한다. 추가 검증 결과는 PR의 최신 체크와 댓글에 기록한다.
- PostgreSQL 실제 권한·동시성·파기·rollback은 기존 CI의 일회용 PostgreSQL 17에서 확인하도록 확장했다. 로컬 Docker daemon이 실행 중이 아니므로 로컬 DB 검증으로 기록하지 않는다. 최종 커밋의 CI 결과와 실행 증적은 [PR #500](https://github.com/bodeul110/bodeul-platform/pull/500)의 체크와 검증 댓글에서 확인한다.
- 수정한 문서 7개의 로컬 링크 434개를 검사했고 끊긴 경로는 없었다.

## 남은 범위

기능 기본값은 계속 OFF다. 실제 DEV의 V24~V26 적용과 runtime 계정 권한 확인, 파기 작업에 새 함수 연결·dry-run, Android 수신·상대방 지정·계정 전환 복구와 두 계정 종단 검증이 남는다. 실제 개발·운영 DB, 기능 플래그, 서버 배포 설정은 변경하지 않았다. 원문 조회 만료가 원문 파기 완료를 뜻하지 않으며 현재 자동 파기 스케줄에 새 함수가 연결된 상태도 아니다.
