# 공용 소유권과 개인 개발 권한 정리

확인일: 2026-11-07

이 문서의 기존 권한 축소 결과와 아래의 후속 작업을 구분한다. GitHub·Vercel·Supabase의 기본 소유 이메일은 전환 후 확인했지만, 나머지 외부 서비스나 복구 리허설까지 완료한 것으로 해석하지 않는다.

## 후속 결과와 소유 기준

- 326 자원 기록을 보존한 뒤 기본 프로젝트는 14:57 KST, 독립 조직은 15:24 KST에 삭제 요청했다. 두 자원 모두 `DELETE_REQUESTED`이며 복구 기간이 남아 있다. Google 계정과 닫힌 결제 계정은 삭제하지 않았다.
- 조직 삭제 전에 발견된 운영 관리자 목록 인증 오류는 관리자 웹 [PR #106](https://github.com/bodeul110/bodeul-admin-web/pull/106)의 운영 전용 OIDC/WIF 읽기 연결로 복구했다. 해당 프로젝트 Production에 기본 Firestore DB get/list만 허용했고 구성용 임시 권한은 회수했다.
- 삭제 후 공식 프로젝트의 기존 IAM·조직·결제 연결, Core API 두 개 `UP`, DB 두 개 `Healthy`, 관리자 목록 두 개 HTTP 200을 확인했다. 운영에는 승인된 목록 reader 바인딩만 추가됐으며 기존 권한은 유지했다.
- 이후 사용자 결정으로 전체 프로젝트의 공식 소유 계정을 `scp@bodeul.kr`로 통일한다. 기존 외부 소유 계정의 이메일 변경을 먼저 사용하고 저장소·팀·프로젝트·DB ID는 유지한다.
- Google 관리자 그룹은 공식 계정 하나만 Owner·Member인 것을 재조회했다. Supabase는 사용자의 이메일 변경 후 로그인·기본 이메일과 조직 Owner가 `scp@bodeul.kr`인 것을 확인했다. MFA와 개인 Developer 두 명, 기존 개발·운영 DB의 ID·정상 상태는 유지된다.
- Vercel은 기존 Owner ID에 `scp@bodeul.kr` 인증·Primary 지정·MFA 등록과 Developer 두 명, 팀·프로젝트·GitHub 연결 유지를 확인했다. GitHub도 기존 `bodeul110` 계정의 인증된 Primary·기본 알림 주소를 공식 주소로 맞추고 MFA 등록 유지와 두 저장소의 소유자·개인 Write를 확인했다.
- GitHub·Vercel의 이전 Gmail은 보조 이메일로 남겼다. 이메일 변경으로 기존 계정 ID·소스·런타임 설정을 재생성하지 않았고 보안·복구 점검의 상세는 비공개 운영 기록에 남긴다.
- 이 후속 문서 정리는 개인 개발자 권한·CLI 기본 계정·자동화 계정·업무 관리자 계정을 공용 계정으로 바꾸는 작업이 아니다. 현재 전환 상태는 [서비스 소유 계정 표](../operations/service-ownership-and-access.md)를 따른다.
- 후속 변경 문서 3개의 UTF-8, 로컬 링크 12개와 `git diff --check`를 확인했다. 문서만 수정했으므로 앱·서버 빌드는 별도로 실행하지 않았다.

아래 항목은 후속 조직 삭제와 이메일 통일 결정 이전에 수행한 권한 축소 단계의 기록이다.

## 판단

- 작업 목적: 공용 소유자, 개인 개발 계정과 임시 326 계정을 명확히 구분한다.
- 선택한 방식: 공용 관리자 실로그인과 현재 IAM을 확인한 뒤 개인 Owner/Editor를 개발 역할로 축소한다.
- 대안: 프로젝트 재생성, 계정 통합, 구 조직 즉시 삭제, Supabase 요금제 변경을 검토했으나 이번 범위에서 제외했다.
- 선택 이유: 현재 MVP의 서비스 식별자·DB·배포 인증을 보존하면서 자산 소유와 일상 작업을 구분할 수 있다.
- 리스크: 공용 관리자 잠금, IAM 전파 지연과 요금제별 역할 차이가 있다. 마지막 소유자를 남기고 실제 개인 권한을 재검증한다.

## 반영 내용

- Google `gcp-admins`에서 개인 계정을 제거하고 공식 관리자만 그룹 Owner로 유지했다.
- 개인 개발 계정을 `developers`와 `prod-operators`의 Member로 등록했다. 개인에게 그룹 소유권은 주지 않았다.
- 개발 그룹의 프로젝트 Editor를 서비스별 사전 정의 역할로 대체했다. 개발 그룹에 등록된 두 구성원의 중복 직접 Editor도 제거했다.
- 개발 Firebase 파일 버킷에만 개발 그룹의 Storage Object User를 부여했다. 운영 파일 버킷은 변경하지 않았다.
- 개발 프로젝트의 나머지 IAM 바인딩과 자동화 계정은 변경 전후 대조하여 보존했다. 운영 프로젝트 IAM, WIF, 런타임·배포 서비스 계정은 변경하지 않았다.
- Vercel·Supabase는 공용 계정만 Owner로 두고 개인 두 명을 각각 Developer로 변경했다.
- Supabase의 미수락 326 Owner 초대를 취소했다.
- GitHub 두 저장소는 이미 공용 계정 Admin·개인 Write 구조여서 변경하지 않았다.
- 플랫폼·웹 저장소의 로컬 Git 작성자를 개인 GitHub 계정과 `noreply` 이메일로 맞췄다. 전역 Git 설정과 기존 커밋 이력은 변경하지 않았다.
- 사용자 개인 로그인 후 Firebase CLI의 메인 저장소·이번 작업 worktree 기본 계정을 개인 계정으로 전환했다. 공용 로그인은 삭제하지 않았다.

`testIamPermissions`는 기재한 권한의 읽기 전용 검사다. 실제 데이터 쓰기·배포·결제는 검증을 위해 실행하지 않았다. 개발 역할의 모든 UI 동작과 앱 업무 종단 검증을 대체하지 않는다. 원본 IAM, 구성원, 비교 결과와 화면은 계정 주소를 포함하므로 비공개 운영 기록으로 보관한다.

## 326 잔여 점검

- 실제 `bodeul-dev`·`bodeul-prod-110`은 공식 `bodeul.kr` 조직 소속이다.
- 구 조직의 Cloud Asset 검색에서는 기본 프로젝트 한 개, 기본 API, 조직 정책과 감사 로그 자원이 확인됐다. 실행 서버·업무 DB·일반 Storage 버킷은 검색 결과에 없었다. 지원되지 않는 자산까지 비어 있다고 단정하지 않는다.
- 기본 프로젝트의 직접 Owner는 326 계정이고 결제는 비활성이다. 연결된 별도 결제 계정은 공식 관리자에게 조회 권한이 없지만 기존 326 자격 증명으로 읽기 확인했다. `open=false`, 상위 조직 없음이며 Billing Admin은 326 계정이다. 결제 연결과 권한은 변경하지 않았다.
- 구 조직의 `bodeul-test`는 닫힌 상태다. 기본 프로젝트의 별도 결제 연결과 같은 계정으로 취급하지 않는다.
- 현행 두 프로젝트의 직접 IAM과 프로젝트 범위 Cloud Asset IAM 검색에서 개인 개발 계정·326 계정의 잔여 직접 바인딩은 발견되지 않았다. 공식 조직 전체 IAM 검색은 조회 권한이 없어 결과 없음으로 기록하지 않았다.
- 구 조직의 직접 임시 계정 권한, 기본 프로젝트와 독립 조직의 소유자 설정은 변경하지 않았다.

## 남은 범위

- Supabase Pro의 Developer는 같은 조직의 운영 DB 콘텐츠에도 접근할 수 있다. 개인 운영 DB 접근까지 제한하려면 별도 접근 구조 결정이 필요하다.
- 구 조직의 독립 소유자 목록과 보존 필요성을 확인하기 전에는 326 조직·기본 프로젝트를 삭제하지 않는다.
- Vercel·Supabase의 상세 청구 상태와 확인 항목은 비공개 운영 기록에 남겼다. 소유권 변경만으로 결제 정상화를 보장하지 않는다.
- Firebase CLI는 폴더별 기본 계정을 선택했으므로 다른 worktree에서는 실행 전 계정을 확인한다. 전역 Git의 326 작성자 설정과 구 계정 자격 증명은 무관한 저장소·복구 접근에 영향을 주므로 그대로 두었다.
- 이번에 사용하지 않은 외부 서비스의 소유권과 Google Payments 권한·결제 수단은 재검증하지 않았다.
- 공용 관리자 복구 리허설과 개인 계정 전체의 MFA 강제는 이번 작업에 포함하지 않았다.
- 앱·서버 소스, 의존성, DB schema·데이터, 배포 브랜치·보호 규칙은 변경하지 않았다.

운영용 계정 선택은 [서비스 소유 계정 표](../operations/service-ownership-and-access.md)를 기준으로 한다.
