# 보호자 예약 서버 원문의 Android 연결

기준일: 2026-10-29

## 설계 판단

- 작업 목적: #419에서 서버에 보관한 동일 예약 원문을 Android가 요청 ID로 다시 불러오고 승인·접수하게 한다.
- 선택한 방식: 직접 본문을 전달하는 기존 Repository를 유지하고, 저장 원문 전용 Repository와 식별자·목록·상대방 표시 모델을 추가한다. Firebase ID token·App Check 전송은 기존 인증 클라이언트를 재사용한다.
- 대안: 원문을 Intent·클립보드·로컬 파일로 전달하거나 기존 직접 본문 API로 자동 재시도하는 방식은 사용하지 않는다.
- 선택 이유: 현재 MVP에서는 서버의 불변 원문과 요청별 인가를 재사용하면 계정 간 원문 복사 없이 수신·복구 화면을 연결할 수 있다. 새 의존성이나 DB 변경은 필요하지 않다.
- 리스크: 데이터 계층 준비는 사용자 화면·실제 DEV 연동·기능 활성화 완료가 아니다. 화면 연결 시 로그아웃과 계정 변경에서 이미 표시한 원문도 지우고, 응답 유실 뒤 같은 요청을 복구하는 UI를 별도로 검증해야 한다.

## 계약

- 저장·목록·상세 응답의 환자/보호자/요청 UUID와 시각을 검증한다. 목록에는 원문과 프로필을 보관하지 않는다. 응답 오류를 빈 목록이나 미승인 상태로 대체하지 않는다.
- 상세 원문은 서버 정규화 응답을 사용하고, 상대방 표시에는 현재 프로필의 이름·마스킹 전화번호만 보관한다. 승인·접수에는 원문을 다시 보내지 않는다.
- 같은 요청의 저장 재시도는 같은 ID와 본문을 사용한다. 오류 뒤 자동 재전송·새 ID 발급·기존 API로 우회하지 않는다.
- 승인 상태 조회·철회는 원문 조회와 분리한다. 원문 만료 또는 보호자 비활성 상태에서도 서버가 허용한 기존 환자의 철회 경로를 사용할 수 있다.
- 접수 재시도는 원문 조회·목록·승인 활성 상태 확인을 선행 조건으로 두지 않는다. 서버가 원문 파기 뒤에도 이미 생성된 최소 접수증을 반환할 수 있기 때문이다. 최초 접수 허용 여부는 여전히 서버의 최신 승인·참여자 검증이 결정한다.
- 각 호출의 동일 인증 세션에서 `/api/auth/me`의 PostgreSQL ID·역할을 확인한다. 전송 전 계정 변경과 콜백 전달 전 계정 변경을 검사해 다른 로그인에 이전 원문을 반환하지 않는다.

`CoreApiGuardianBookingDraftRepository`는 `GuardianBookingDraftRepository`를 구현한다. `submitDraft/listDrafts/loadDraft`는 각각 식별자 요약·불변 목록·서버 정규화 원문을 반환한다. `loadApproval/revokeDraft`는 원문 없이 식별자만 받으며 `grantDraft/createDraft`는 저장 요청 경로에 버전·확인 또는 승인 ID만 보낸다. 전체 원문·상대방 표시 모델은 Parcelable·Serializable이나 로컬 저장소를 구현하지 않는다.

인증 클라이언트에 요청을 시작한 Firebase UID를 명시해 다른 계정의 토큰을 가져오지 않게 한다. 추가 전송 전과 결과 콜백에서도 현재 계정을 비교한다. 접수 POST 전 인증 준비 실패는 `NOT_SENT`, 서버 확정 거부는 `REJECTED`, 전송 후 단절·5xx·깨진 성공 응답은 `UNKNOWN`이다. 계정 변경으로 버린 결과는 호출자에게 일반 오류로 전달하며, 미접수로 재분류하지 않는다. 향후 화면은 이 오류만으로 새 요청을 만들지 않고 이전 요청의 결과 불확실성을 유지해야 한다.

## 범위

Android 데이터 계층과 단위 계약 검증만 변경한다. 일반 메뉴·release 진입점·화면 로컬 보관·원격 DB·기능 플래그·서버·관리자 웹 권한은 변경하지 않는다. 실제 수신 목록, 상대방 지정, 프로세스 종료 후 요청 선택 및 두 계정 종단 검증은 후속 범위다.

로컬 검증과 확인하지 않은 범위는 [검증 기록](../reports/issue-419-android-draft-repository-2026-10-29.md)에 구분한다.
