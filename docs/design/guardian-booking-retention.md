# 보호자 예약 원문 정기 파기

## 설계 판단

- 작업 목적: #419의 예약 원문 만료가 실제 원문 파기로 이어지도록 기존 정기 보존 작업에 연결한다.
- 선택한 방식: 전용 플래그는 기본 OFF로 유지하고 기존 Functions 작업에서 V26의 건수 조회·제한된 파기 함수를 호출한다. V27은 원문 없이 후보·파기·잔여 건수만 기존 실행 이력과 월간 보고에 추가한다.
- 대안: 별도 서버·스케줄 생성, 조회 요청에서 즉시 파기, 건수 이력 없이 로그만 남기는 방식을 검토했다.
- 선택 이유: 현재 MVP에서는 기존 dry-run·apply·TLS·최소 권한 경계를 재사용하는 편이 운영 지점을 늘리지 않고 파기 실패를 추적할 수 있다.
- 리스크: 접근 만료와 물리 파기 시각은 다르다. 기존 일일 스케줄을 유지하므로 만료 즉시 삭제를 보장하지 않으며, 배치 한도·잠금 경합으로 남은 원문은 잔여 건수로 표시하고 다음 실행에서 재시도한다. 실제 환경 검증 전 예약 기능을 켜지 않는다.

## 실행 경계

- `RETENTION_GUARDIAN_BOOKING_ENABLED=true`를 명시해야 새 후보 조회·파기 경로를 사용한다. OFF에서는 V26·V27 객체나 새 집계 키를 요구하지 않는다.
- 플래그 ON은 삭제 승인이 아니다. 정기 작업의 `RETENTION_APPLY_ENABLED`와 수동 실행의 `--dry-run`·`--apply` 구분을 유지한다.
- V27 집계 반환 계약을 파기 전에 확인한다. V26만 적용됐거나 조회 권한이 없으면 다른 데이터 파기 시작 전 실패로 기록한다.
- 한 실행에서 최대 10배치, 배치당 최대 500건을 처리한다. 만료 기준은 실행 시작 시각으로 고정하고 DB의 현재 시각 상한도 유지한다. 마지막에 잔여 후보를 다시 조회한다.
- 원문 JSON만 NULL로 만들며 요청 ID 재사용 방지용 참여자·해시·시각은 유지한다. 예약·승인·감사·정보공유 권한은 변경하지 않는다.
- 월간 잔여 건수는 여러 실행의 합이 아니라 해당 월의 마지막 활성 실행 보고값이다. 성공 시 마지막 후보 재조회 값이며, 중간 실패 시 처음 후보에서 확인된 파기 건수만 뺀 추정치일 수 있다. 활성 실행 수·실패 수를 함께 보고 미실행과 0건 성공을 구분한다. 집계는 개인정보를 포함하지 않는다.
- V27 rollback은 실행 중 작업 또는 새 집계 이력이 있으면 거부한다. 실제 이력 삭제로 rollback을 강행하지 않는다.

## 적용 순서와 영향

개발 DB의 V24~V27 적용과 runtime 권한 확인, 새 경로 dry-run, 합성 원문 파기·재실행·정리 검증 후 실제 활성화 여부를 판단한다. Functions 배포·환경변수 변경·실제 DB migration·삭제 apply는 이 소스 구현과 별도 승인 작업이다.

Android·관리자 웹 UI 및 역할은 바꾸지 않는다. 기존 월간 보고 컬럼 이름·권한은 유지하고 새 건수 필드만 추가한다. 관리자 서버는 새 원문이나 테이블 권한을 받지 않는다. 기존 집계 입력은 V27 이후에도 허용한다.

## 회귀 검증

`core-api`의 `db/verification/verify_guardian_booking_approval_migration.sh`는 CI의 새 로컬 PostgreSQL DB에서 Java 권한·rollback 테스트와 `functions/postgres-tests/guardian-booking-retention.test.js`를 실행한다. Node 22와 Functions lockfile의 의존성을 사용하며, 후자는 실제 파기 실행기와 원문 SQL·집계를 연결해 검증한다. 일반 Functions 단위 테스트와 별도이며 실제 개발·운영 DB에서는 실행하지 않는다.
