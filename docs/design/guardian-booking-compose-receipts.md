# 보호자 대리예약 작성과 접수 확인 (#419)

- 작업 목적: 수신함의 환자 승인 전후를 연결해 보호자가 승인 요청을 작성하고, 본인이 접수한 결과를 앱 재실행 후에도 확인한다.
- 선택한 방식: 환자가 자기 수신함에서 확인한 Core API 환자 코드를 직접 전달한다. 보호자는 환자 코드와 프로필 이름·연락처를 입력하고 병원·진료과 선택기를 재사용한다. 승인 요청 전송과 실제 예약 접수는 서로 다른 버튼이다.
- 대안: 환자를 전화번호로 검색하거나 원문·승인 ID를 휴대폰에 저장하지 않는다. 접수 확인은 예약 생성 POST를 재전송하지 않고 읽기 전용 목록을 조회한다.
- 선택 이유: 서버에 이미 신청자, 보호자, 요청 ID와 접수 번호가 있어 새 DB 테이블이나 별도 정보공유 동의 없이 두 계정의 경계를 유지할 수 있다.
- 리스크: 목록은 본인이 신청한 최신 50건 중 현재 참여 자격이 확인된 건만 표시한다. 조회 실패나 빈 목록만으로 미접수를 단정하지 않는다. 실제 개발 계정 두 개로 검증하기 전까지 개발 플래그는 기본 해제, 릴리스는 항상 해제한다.

관리자 웹·예약 수정/취소·위치/채팅/건강정보 열람 권한·운영 설정에는 변경이 없다.

일반 수신함 진입에는 개발 플래그, Firebase 인증을 쓰는 빌드, Android 8(API 26) 이상이 필요하다. 기존 승인 모델이 `java.time`을 쓰므로 Android 7에서는 이 선택 기능만 열지 않는다. 앱 전체의 최소 버전이나 환자 본인 예약은 바꾸지 않는다.

## 사용 순서

1. 환자는 일정·이력의 보호자 예약 수신함에서 **내 환자 코드 확인**을 눌러 지정할 보호자에게만 전달한다.
2. 보호자는 예약의 가족 선택 또는 일정·이력에서 수신함에 들어간다. **대리예약 작성**으로 병원·진료과를 고른 뒤 환자 코드, 프로필 이름·전화번호와 동행 내용을 확인해 승인 요청을 보낸다.
3. 환자는 수신함에서 원문과 보호자를 확인해 성인 본인 승인을 한다. 보호자는 해당 요청을 다시 열어 **승인된 내용으로 예약 접수**를 누른다. 승인 요청만으로 예약이 생성되지는 않는다.
4. 접수 응답이 끊겼다면 **이 요청의 접수증 확인**으로 해당 요청만 조회한다. 앱을 다시 연 뒤에는 **내 최근 접수증**에서 요청 번호와 접수 번호를 대조한다. 다른 환자의 요청이나 기존 예약의 상세로 이동하지 않는다.

승인 요청의 저장 응답을 잃으면 같은 화면에서는 수정 없이 같은 요청 ID와 본문으로만 다시 보낸다. 화면을 떠나면 본문·코드·승인은 지우고, 재진입 시 서버 수신함에서 확인한다. 기기에는 복구용 파일이나 승인 정보를 남기지 않는다.

## 개발 환경 확인 (2026-11-20)

`bodeul-db-dev`를 읽기 전용으로 확인한 결과 마지막 성공한 Flyway 버전은 V23이다. V24~V27 성공 이력, 승인·원문 테이블과 원문 파기 함수는 없었다. 개발 Core API의 최신 준비 리비전 `bodeul-core-api-preview-00035-65n`에는 기능 활성화 환경변수가 설정되지 않았다. 격리 DB 검증과 실제 DEV 계정 검증은 별개다.

다음 순서는 개발 DB migration → runtime 권한·원문 파기 스케줄 및 dry-run 확인 → 승인된 개발 환경만 활성화 → 환자·보호자 두 계정으로 전송·승인·접수·재로그인 후 복구 확인이다. 운영 환경에는 적용하지 않는다.
