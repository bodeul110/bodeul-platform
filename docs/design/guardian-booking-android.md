# 보호자 예약 Android 연결

기준일: 2026-10-28

## 설계 판단

- 작업 목적: #419의 기존 승인 API를 Android에서 동일 본문·요청 ID로 호출하고 검토·철회·접수 상태를 검증한다.
- 선택한 방식: 전용 Repository와 화면 Coordinator를 분리하고 기존 Firebase/App Check 인증 클라이언트를 재사용한다. 사용자 진입 없이 debug 합성 화면에서 먼저 검증한다.
- 대안: 예약 생성 권한을 기존 정보공유 동의에 합치거나, 민감한 예약 원문을 외부 링크·클립보드로 전달하는 방식은 채택하지 않는다.
- 선택 이유: 현재 API는 승인 메타데이터만 저장하므로 요청 원문 전달이 별도로 필요하다. MVP에서는 기존 인가를 유지하며 검증 가능한 클라이언트 연결부터 나누는 편이 안전하다.
- 리스크: 이 변경만으로 실제 보호자 예약을 사용할 수 없다. 앱 내부의 요청 전달·수신 경로, 환자가 확인할 상대방의 신뢰 가능한 표시 정보, DEV migration·권한·종단 검증이 남는다.

## 변경 범위

환자 승인과 보호자 접수는 기존 `/api/appointments/guardian-booking`만 사용한다. 매 호출에서 같은 토큰의 `/api/auth/me`로 PostgreSQL 사용자 ID와 역할을 확인한다. Firebase UID를 PostgreSQL UUID로 오인하지 않는다. 서버의 정규화된 본문을 환자에게 표시하고 승인·재시도에 보존한다.

조회 오류는 미승인(version 0)으로 만들지 않는다. 승인·철회 오류 뒤에는 재조회와 재확인이 필요하다. 접수 결과가 불명확하면 같은 요청 본문·승인·요청 ID만 재전송하며 기존 예약 API나 Firestore로 우회하지 않는다. 접수증만 표시하고 상세·리포트·취소 권한은 추가하지 않는다.

현재 승인 조회가 성공했지만 지난 예약이나 프로필 변경 때문에 미리보기가 400/409로 거부되면, 검증되지 않은 본문은 숨기고 기존 승인 철회만 허용한다. 철회 후에도 새 승인은 열지 않는다. 인증·권한·연결 오류는 이 경로로 흡수하지 않는다.

원문 전달 경로가 없는 현재 일반 사용자 메뉴와 release 진입점은 추가하지 않는다. debug 화면은 합성 Repository만 사용하며 이 승인 흐름에서 로그인·서버·DB를 호출하지 않는다. 화면 종료와 재생성 시 로컬 승인 상태를 폐기한다. 실제 DB, 서버 기능 플래그, 의존성, 관리자 웹은 변경하지 않는다.

검증 결과는 [Android 승인 연결 검증](../reports/issue-419-android-approval-2026-10-28.md)에 기록한다. 단위 테스트의 가짜 전송 응답, 에뮬레이터 합성 화면, 실제 인증된 DEV 종단 검증은 서로 다른 증거다.

## 생성 실패 복구

- 작업 목적: 승인 v1 조회 후 환자가 v2로 재승인했을 때, 생성 거부를 응답 유실로 오인해 v1 재시도에 갇히는 문제를 막는다.
- 선택한 방식: 생성 결과에 `NOT_SENT`, `REJECTED`, `UNKNOWN`을 구분하고 Coordinator에서 재조회 또는 동일 요청 재시도를 선택한다.
- 대안: 오류 문구에서 상태 코드를 추측하거나 모든 Repository의 공용 오류 인터페이스를 바꾸는 방식은 채택하지 않는다.
- 선택 이유: 현재 MVP의 이 생성 경로에만 결과 불확실성 판단이 필요하므로, 공용 인증 클라이언트와 다른 화면을 바꾸지 않는 전용 결과 타입으로 영향 범위를 제한한다.
- 리스크: 앞선 생성 응답이 유실됐다면 이후 재시도 거부만으로 미생성을 확정할 수 없다. 같은 요청을 유지하며, 화면 종료 후 결과 복구는 서버 조회 경로와 함께 후속으로 해결해야 한다.

| 생성 시도 결과 | 첫 시도 후 동작 |
| --- | --- |
| 토큰 준비·참여자 확인 등 POST 전 실패 (`NOT_SENT`) | `ERROR`로 전환해 로그인·승인 상태 재조회 허용 |
| POST의 HTTP 400·401·403·404·405·409·422 (`REJECTED`) | `ERROR`로 전환하고 오래된 승인을 버림. 동일 요청 ID로 최신 승인 조회 후 접수 가능 |
| 전송 후 연결 오류, 5xx, 그 외 미분류 상태, 잘못된 성공 응답 (`UNKNOWN`) | `UNCERTAIN`으로 전환하고 원래 본문·승인·요청 ID로만 재시도 |

이미 `UNCERTAIN`이 된 요청은 다음 시도가 `NOT_SENT`나 `REJECTED`여도 불확실성을 유지한다. 새 승인으로 바꾸거나 새 요청을 만들지 않으며, 재확인 실패와 앞선 요청 결과 미확정을 함께 안내한다. UI에는 서버 원문 오류나 비밀값을 노출하지 않는다.

## 남은 범위

- 인가된 앱 내부 요청 원문 전달·수신 및 상대방 식별 정보 검토 화면 연결
- 실제 화면 연결 시 로그아웃·계정 변경에서 Coordinator를 폐기하고 화면의 원문을 지우기. 프로세스 종료 후에도 같은 요청을 찾을 수 있는 인가된 서버 경로와 접수 결과 복구
- 비활성 보호자의 기존 승인을 환자가 새로 조회해 철회하는 서버 경계 보완. 현재 GET은 양쪽 활성 계정을 요구하지만 revoke는 환자 활성만 요구해, 화면을 새로 열면 조회부터 차단될 수 있음
- 실제 DEV V24·V25 적용 여부와 계정 상태 조회 권한 확인
- 두 참여자 실제 로그인으로 승인·철회·생성·재시도와 권한 거부 검증
- 운영 활성화는 별도 승인과 검증 후 진행
