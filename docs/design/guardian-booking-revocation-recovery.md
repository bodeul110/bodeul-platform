# 보호자 비활성 이후 예약 승인 철회

기준일: 2026-10-28

## 설계 판단

- 작업 목적: 보호자가 비활성화된 뒤에도 환자가 자신이 남긴 예약 생성 승인을 조회하고 철회할 수 있게 한다.
- 선택한 방식: 기존 승인 GET에 환자 본인·활성 계정 검사를 적용하고, 보호자를 더 이상 사용할 수 없으면 해당 환자의 기존 승인 메타데이터만 `revocationOnly=true`로 반환한다. 앱은 이 응답에서 미리보기·신규 승인을 열지 않는다.
- 대안: 모든 참여자 검사를 완화하거나, 앱에서 403을 무조건 무시하고 철회 화면을 여는 방식은 채택하지 않는다.
- 선택 이유: 현재 MVP의 승인 저장소와 철회 API를 그대로 사용하면서, 이미 허용된 환자 본인의 철회 권한까지 조회 단계에서 막히는 불일치만 해소할 수 있다.
- 리스크: 조회 결과는 현재 상태의 안내이지 이후 쓰기의 권한 증명이 아니다. 승인·생성은 매번 양쪽 계정을 재검사하고, 계정 상태 조회 장애는 비활성으로 단정하지 않고 실패 처리한다.

## 허용 범위

| 요청 | 처리 |
| --- | --- |
| 활성 환자 본인, 기존 승인 있음, 보호자 비활성·삭제·역할 변경 | 본인의 해당 요청 승인 메타데이터 조회와 기존 철회 허용 |
| 같은 조건이나 기존 승인 없음 | 조회 거부. 보호자 계정 상태를 확인하는 신규 조회로 사용하지 않음 |
| 비활성 환자, 변경된 환자 신원, 다른 환자·매니저 | 조회·철회 거부 |
| 보호자가 승인 조회·접수를 시도 | 기존 양쪽 활성 계정·역할 검사 유지 |
| 새로운 승인·미리보기·예약 생성 | 기존 양쪽 활성 계정·역할 검사 유지 |
| Firebase 계정 상태 확인 장애 | 503. 활성 또는 비활성으로 추정하지 않음 |

## API와 앱

기존 승인 응답에 Boolean `revocationOnly`를 추가한다. GET에서 `true`면 환자가 자신의 기존 승인 상태만 확인하고 철회할 수 있다는 화면 모드다. 승인 ID·버전·시각 이외의 보호자 계정 상태, 예약 원문, 개인정보, fingerprint는 추가로 반환하지 않는다. `active`는 기존 승인 정책·시간 조건의 유효성을 나타내며 참여 계정의 활성 여부를 대신하지 않는다.

Android는 `revocationOnly=true`를 받은 환자에게 기존 승인 메타데이터와 철회만 제공하며 POST 미리보기를 호출하지 않는다. 보호자에게 이 모드가 내려오거나 승인 이력 없는 응답과 결합되면 응답 오류로 처리한다. 구서버가 필드를 생략하면 기존 미리보기 경로를 유지하고, 필드가 있으면 문자열·숫자·null을 Boolean으로 강제 변환하지 않는다. 일반 401/403/503을 철회 모드로 바꾸지 않는다.

철회는 기존 승인 버전과 환자 본인을 서버에서 다시 확인한다. 이미 접수된 예약 취소나 정보공유 동의 변경은 포함하지 않는다. 조회 후 보호자 상태가 바뀌어도 승인·생성 서버 검사를 우회하지 못한다.

## 변경하지 않는 범위

- DB schema·migration·runtime role 권한·실제 데이터
- 기능 플래그의 기본 OFF, 일반 사용자 메뉴·release 진입점, 배포 설정
- 관리자 웹의 기존 계약과 코드. 추가 응답 필드는 보호자 예약 Android 연결에서만 사용한다.
- 예약 원문 전달·표시 정보·프로세스 종료 후 복구와 실제 DEV 종단 검증

검증 결과는 별도 작업 보고서에 기록한다. 합성 계정의 단위·HTTP 계약 테스트와 격리 DB 테스트를 실제 개발·운영 환경 성공으로 간주하지 않는다.
