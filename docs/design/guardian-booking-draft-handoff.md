# 보호자 예약 원문 전달

## 설계 판단

- 작업 목적: #419에서 환자와 보호자가 같은 예약 원문을 서버에서 다시 불러오고, 그 원문으로 승인·접수를 이어가게 한다.
- 선택한 방식: 보호자와 요청 ID를 키로 하는 불변 초안을 별도 서버 전용 테이블에 저장한다. 지정 환자와 작성 보호자만 조회하며 현재 DB 역할과 Firebase 활성 상태를 다시 확인한다.
- 대안: 단말 간 원문 전달, 클라이언트의 수정 가능한 임시 문서, 기존 승인 감사 테이블에 원문을 넣는 방식을 검토했다.
- 선택 이유: 현재 MVP에서는 기존 PostgreSQL·Core API로 요청 단위 전달과 재시도를 처리할 수 있다. 승인 감사와 민감한 예약 원문의 보존 범위도 분리할 수 있다.
- 리스크: 원문에는 건강·연락 정보가 포함된다. 접근 만료와 물리적 삭제는 구분하며, 만료 원문 파기 작업 연결·DEV 검증 전에는 기능을 활성화하지 않는다. Firebase와 PostgreSQL 사이에 분산 트랜잭션이 있다고 가정하지 않는다.

## 범위

원문은 정규화와 현재 환자 프로필 일치 검사를 거친 뒤 저장한다. 다른 환자를 검색하는 API나 계정 간 영구 관계는 추가하지 않는다. 보호자는 기존에 전달받은 환자 UUID와 이름·연락처를 사용해야 하며, 사용자 화면의 상대방 지정 절차는 후속 연결 대상이다.

같은 보호자·요청 ID로 다른 환자나 본문을 덮어쓸 수 없다. 내용 변경은 새 요청 ID와 새 환자 승인을 요구한다. 동일 요청의 재전송은 최초 저장 시각과 만료 시각을 유지한다. 원문 조회에서 상대방의 이름과 마스킹한 전화번호만 현재 프로필에서 표시하며 이메일이나 Firebase UID를 추가로 공개하지 않는다. 이는 연락처 실명·본인 인증을 뜻하지 않는다.

원문 파기 후에도 요청 키·참여자 UUID·해시·시각은 남겨 같은 ID의 부활을 막는다. 이름·연락처·건강정보를 포함한 JSON 원문은 NULL로 제거한다. 계정 삭제 영향도는 이 최소 기록 수, 남은 원문 수, 활성 원문 수를 구분한다. 최소 기록의 정리는 계정 삭제·보존 절차와 함께 다루며, 이 기능이 모든 개인정보의 삭제를 완료했다고 표시하지 않는다.

조회 가능 기간은 저장 후 최대 24시간과 예약 시각 중 이른 때까지다. 보호자별 활성 초안은 20건으로 제한한다. 서버 원문에서 승인·예약 생성을 수행하며, 접수 후 재시도는 원문 만료·파기와 관계없이 기존 최소 접수증만 확인한다. 예약 상태·리포트·위치·채팅의 열람 동의는 자동 부여하지 않는다.

## 배포 경계

`bodeul.guardian-booking.enabled=false`를 유지한다. V26은 소스와 격리 DB 검증용으로 추가하며 실제 개발·운영 DB에는 적용하지 않는다. 파기 전용 SQL은 건수만 미리 보거나 만료 원문만 제한된 배치로 지우며 예약·승인·감사는 변경하지 않는다. 예약 원문을 읽지 않는 기존 파기 작업에 이 SQL을 연결하고 dry-run을 검증한 뒤 기능 활성화를 판단한다.

관리자 웹에 새 테이블 권한이나 API를 제공하지 않는다. Android 일반 화면·알림·실제 두 계정 연동은 이번 서버 작업과 구분한다.
