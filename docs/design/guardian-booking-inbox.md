# 보호자 예약 수신함

## 설계 판단

- 작업 목적: #419의 서버 저장 원문을 환자·보호자가 목록에서 찾아 확인하고 환자가 승인·철회할 수 있는 Android 화면을 연결한다.
- 선택한 방식: 식별자·시각만 있는 목록과 상세 조회를 분리한다. Coordinator가 조회 세대와 로그인 계정을 묶고 화면은 현재 서버 프로필의 이름·마스킹 전화번호와 원문을 표시한다.
- 대안: 기존 직접 본문 전달 화면에 임의 원문을 넣거나 민감한 원문을 Intent·Bundle·로컬 저장소에 보관하는 방식은 사용하지 않는다.
- 선택 이유: 현재 MVP에서는 기존 원문 API와 요청별 인가를 재사용하면 된다. 재진입 시 서버 목록을 다시 조회하는 편이 계정 간 원문 잔류와 오래된 승인 재사용을 줄인다.
- 리스크: 목록은 활성 요청의 최신 50건만 제공한다. 파기된 요청의 접수 복구, 보호자의 새 요청 작성·상대방 지정, 실제 DEV 두 계정 연동은 이 화면만으로 해결되지 않는다.

## 범위와 경계

일정·이력에 수신함 진입점을 준비하되 개발 빌드의 `bodeulGuardianBookingInboxEnabled`는 기본 `false`, Release는 항상 `false`다. 실제 환경 설정이나 서버의 기능 플래그는 바꾸지 않는다. 화면 Activity는 외부로 공개하지 않으며 외부 요청 ID나 원문을 받지 않는다.

목록에는 요청 순번과 접수·만료 시각만 표시한다. 상세와 승인 조회가 모두 성공해야 본문과 새 승인 버튼을 표시한다. 명시적인 `revocationOnly=true`는 원문 조회 없이 기존 승인 철회만 제공하며, 일반 조회 실패를 이 모드로 해석하지 않는다. 승인·철회 응답 유실 또는 버전 불일치는 본문과 작업 버튼을 지우고 재조회하도록 한다.

로그아웃·계정 변경은 즉시 화면을 닫고 이전 계정 콜백을 폐기한다. 백그라운드 전환·재생성에서도 목록·상세·확인 체크를 버리고 서버 목록부터 다시 조회한다. 화면 원문·참여자·승인 정보를 Bundle·Intent·SharedPreferences에 저장하지 않으며 화면 캡처·최근 앱 미리보기는 `FLAG_SECURE`로 차단한다.

예약 생성 승인은 정보공유 동의가 아니다. 수신함에서는 새 예약 접수, 접수증 복구, 기존 예약 취소, 건강정보·위치·채팅·첨부·리포트 권한을 만들지 않는다. 관리자 웹, 서버 계약, DB migration, Functions 배포, 보존 작업 apply에도 변경이 없다.

## 검증과 남은 작업

검증 결과는 [수신함 구현 기록](../reports/issue-419-guardian-booking-inbox-2026-11-07.md)에 남긴다. 합성 Repository 화면 검증과 실제 인증된 DEV 연동은 구분한다.

실제 개방 전에는 V24~V27 적용·계정 상태 조회와 원문 파기 권한·파기 스케줄, 보호자 요청 작성·상대방 지정, 접수 유실 복구 및 두 계정 DEV 검증이 필요하다. #419는 전체 완료로 처리하지 않는다.
