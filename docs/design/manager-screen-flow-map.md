# 매니저 화면 Figma·Android 비교 및 설계안

기준일: 2026-08-29

## 문서 목적

Figma의 매니저 화면 흐름과 현재 Android 구현을 화면 단위로 비교하고, 프론트엔드가 바로 구현할 부분과 서버·제품 계약을 기다려야 하는 부분을 구분한다.

이 문서에서 Figma는 화면 구조와 시각 위계의 기준이다. 기능 완료 여부와 데이터 계약은 Android·Core API 코드와 아키텍처 문서를 기준으로 판단한다. Figma에 화면이 있다는 이유만으로 미구현 기능을 작동하는 기능처럼 노출하지 않는다.

## 비교 기준

- Figma: `보들 가이드`, Page 2, 기준 node `460:2`
- Figma 화면 지도: [Figma 현행 화면 지도](figma-current-screen-map.md)
- 현재 구현: Android `app/`의 매니저 Activity, 화면 모델, Core API 연결
- 단계 계약: [동행 가이드 단계 계약](../architecture/companion-guide-step-contract.md)
- 제품·디자인·구현 책임: [기획·디자인·구현 기준](../planning/source-of-truth.md)

2026-08-25 재확인에서는 Figma Starter 요금제의 MCP 호출 한도에 도달했다. 따라서 node 목록과 화면 구조는 2026-08-22에 확보한 메타데이터와 실기기 캡처를 사용했으며, 픽셀 단위 값은 한도 복구 뒤 다시 검증한다.

## 한눈에 보는 결론

| 판단 | 적용 화면 | 방향 |
| --- | --- | --- |
| 유지하고 시각 보정 | 로그인, 역할 선택, 권한, 채팅, 이력, 내 정보, 문의 | 현재 실제 기능과 Android 정책을 유지하면서 Figma의 정보 위계만 맞춘다. |
| 같은 화면에서 상태 분리 | 자격 인증, 매니저 홈, 동행 가이드 | Figma 프레임마다 Activity를 만들지 않고 서버 상태에 따라 카드·입력·CTA를 교체한다. |
| 운영 진입점 숨김 | 요청 목록, 요청 상세, 매니저 직접 수락 | self-accept API와 개인정보 공개 계약이 생길 때까지 작동하는 화면처럼 노출하지 않는다. |
| 부분 기능만 노출 | 결제 증빙, 처방 이미지, 동행 종료, 매니저 일지 | 현재 저장 가능한 메모·리포트만 제공하고 전용 계약이 없는 입력은 숨긴다. |

따라서 목표는 Figma 화면 수를 그대로 복제하는 것이 아니라, Figma의 사용자 경험을 현재 서버 상태와 안전하게 연결하는 것이다.

## 상태 표기

| 상태 | 의미 | 운영 앱 처리 |
| --- | --- | --- |
| 구현 | 현재 API와 화면이 연결되어 실제 사용 가능 | 정상 노출 |
| 부분 구현 | 핵심 흐름은 있으나 Figma의 세부 입력·상태가 일부 없음 | 가능한 기능만 노출하고 한계를 안내 |
| 계약 대기 | 제품 정책이나 서버 API가 없어 프론트만으로 완료할 수 없음 | 진입점 또는 CTA 숨김 |
| 시각 보정 | 기능은 있으나 Figma와 간격·서체·위계가 다름 | 기능 유지 후 스타일만 조정 |
| 앱 고유 | Figma에 직접 대응하는 화면은 없지만 현재 앱에 필요한 기능 | 역할과 책임이 겹치지 않으면 유지 |

## 목표 사용자 흐름

```text
로그인
  → 사용자 유형 선택
  → 서비스 준비·필요 시점 권한 안내
  → 매니저 자격 서류 제출
      ├─ 미제출·보완 요청 → 서류 등록
      ├─ 검토 중 → 검토 상태 안내
      └─ 승인 완료 → 매니저 홈
          ├─ 활성 동행 없음 → 서류·일정·이력·문의
          │                    └─ 요청 수락은 서버 계약 전까지 숨김
          └─ 활성 동행 있음 → 현재 동행 카드
                               ├─ 단계별 동행 가이드
                               ├─ 안심 채팅
                               └─ 동행 종료 → 최종 리포트 → 이력 상세
```

핵심 원칙은 `화면 개수`가 아니라 `사용자 상태`가 내비게이션을 결정하는 것이다. Figma의 승인 전·승인 후 홈이나 가이드 1~13은 별도 앱 구조가 아니라 같은 화면의 서버 상태별 표현으로 구현한다.

## 화면별 목표 상태

### 1. 자격 인증

한 화면에 모든 상태를 길게 쌓지 않고 서버의 심사 상태에 따라 주 작업을 하나만 강조한다.

| 서버·앱 상태 | 첫 번째 카드 | 주요 CTA | 보조 정보 |
| --- | --- | --- | --- |
| 미제출 | 직무 자격 증빙 1종 안내 | `자격 증빙 선택` | JPEG·PNG·WebP, 10 MiB 이하 |
| 제출 완료 | 제출 파일 요약 | 없음 또는 `파일 교체` | 제출 시각 |
| 검토 중 | 검토 상태 | 비활성 `검토 중` | 예상 처리 안내 |
| 보완 요청 | 보완 사유 | `다시 제출` | 기존 파일과 요청 내용 |
| 승인 완료 | 승인 결과 | `매니저 홈으로` | 승인된 자격 요약 |

OCR 결과나 자동 승인 기능이 서버에 없으면 `분석 중`, `자동 확인 완료` 같은 상태를 만들지 않는다.

### 2. 매니저 홈

공통 구조는 `인사 → 현재 상태 hero → 주요 작업 → 빠른 관리 → 하단 내비게이션`으로 고정한다.

| 홈 상태 | hero | 첫 번째 CTA | 노출 정보 |
| --- | --- | --- | --- |
| 승인 대기 | 자격 검토 상태 | 서류 확인 | 제출 상태, 문의 |
| 승인 완료·미배정 | 활동 준비 상태 | 일정 관리 | 서류, 일정, 이력, 문의 |
| 활성 동행 | 현재 환자·병원·단계 | 가이드 이어가기 | 예약 시각, 보호자, 채팅 |
| 동행 종료 | 최근 완료 요약 | 리포트 확인 | 완료 시각, 이력 |

하단 목적지는 `홈`, `이력`, `가이드`, `내 정보`로 유지한다. 채팅은 현재 동행에 종속되므로 최상위 탭으로 만들지 않는다. 활성 세션이 없을 때 가이드 탭은 빈 상태를 보여주며 임의 세션을 만들지 않는다.

### 3. 요청 목록·상세·매칭 완료

Figma에는 닫힌 흐름이 있지만 현재 배정은 관리자 서버가 담당하고 매니저 self-accept API는 없다. 따라서 프론트 화면을 먼저 공개하면 실제로는 수락할 수 없거나 개인정보를 과도하게 보여주는 문제가 생긴다.

구현 전 확정해야 할 계약은 다음과 같다.

1. 매니저에게 공개할 요청 목록 필드
2. 수락 전 환자·보호자 개인정보 범위
3. 선착순 충돌 시 HTTP 상태와 사용자 문구
4. 매니저 가용 일정 검증 책임
5. 수락 성공 뒤 세션·가이드 snapshot 생성 보장

이 계약 전에는 운영 진입점을 숨기고, Figma와의 시각 비교가 필요하면 실제 API와 연결되지 않는 Debug 전용 preview로만 관리한다.

| 11 | `846:1916` | `MEDICATION_CONFIRMATION` | 처방전·약국·복약 상태와 메모 | Figma 표현 세부 조정 필요 | 기존 저장 기능 유지 후 시각 보정 |
| 12 | `857:7252` | `CARE_COMPLETION` | 보호자 공유와 `동행 종료` CTA | `careEndedAt`이 최종 완료와 분리되지 않음 | 서버가 분리하기 전 독립 완료 상태를 만들지 않음 |
| 13 | `846:2576` | `MANAGER_JOURNAL` | 기존 최종 리포트 제출 | 300자 일지 전용 필드·빈 값 정책 없음 | 기존 리포트 범위만 제출하고 전용 계약 뒤 분리 |

가이드 공통 화면은 다음 순서로 구성한다.

```text
상단 앱바
→ 환자·예약 요약
→ 현재 단계 안내
→ 현재 단계에 필요한 입력 영역만 표시
→ 보조 동작(지도·채팅·파일 선택)
→ 하단 고정 주요 CTA
```

서버 응답의 `steps`, `currentStepCode`, `canAdvance`, `blockedReason`을 우선한다. `GUIDE_NOT_READY`에서는 입력 영역을 숨기고 `가이드 준비 중`만 표시한다. 유효하지만 앱이 모르는 코드는 순번으로 기존 기능을 추정하지 않고 공통 메모만 제공한다.

### 5. 채팅과 최종 리포트

- 채팅은 사용자 간 직접 메시지·첨부·읽음·재시도라는 현재 기능을 유지한다.
- Figma의 단계 이벤트 메시지는 서버가 저장하거나 전송하는 계약이 생길 때만 추가한다.
- 가이드에서 리포트를 작성한 뒤에는 이력 상세에서 읽기 전용으로 확인하는 구조가 적절하다.
- 작성 화면과 조회 화면에서 같은 입력 폼을 재사용하지 않는다. 조회 화면은 수정 가능 여부를 서버 상태로 결정한다.

## 기능이 없는 Figma 화면의 처리 원칙

| 상황 | 설계 방법 | 예시 |
| --- | --- | --- |
| 서버 API와 정책이 있음 | 실제 기능으로 구현 | 직접 채팅, 현재 가이드 조회 |
| 조회만 가능 | 읽기 전용 화면으로 구현 | 완료된 리포트 상세 |
| 일부 저장만 가능 | 가능한 입력만 표시하고 범위를 설명 | 수납·처방 공통 메모 |
| 서버 API가 없음 | 운영 진입점과 CTA 숨김 | 매니저 요청 self-accept |
| 디자인 검토만 필요 | Debug 전용 preview 또는 fixture 사용 | 요청 목록·상세 시안 |
| 데이터가 일시적으로 없음 | 빈 상태·준비 상태 표시 | `GUIDE_NOT_READY` |
| 제품 정책이 미정 | 확정된 문구와 필수 표시를 넣지 않음 | 증빙 최소 장수, 일지 필수 여부 |

`준비 중`은 실제로 준비 작업이 진행되거나 서버가 준비 상태를 반환할 때만 사용한다. 구현 계획조차 확정되지 않은 기능을 `준비 중`으로 상시 노출하지 않는다.

## 프론트엔드 구현 순서

### 1단계: 현재 PR 범위

- 매니저 하위 화면에서 역할에 맞는 홈 복귀
- 가이드의 전체 기능 묶음을 현재 단계별 영역으로 분리
- 단계별 CTA 문구와 하단 고정 버튼
- 미지원 단계와 `GUIDE_NOT_READY` 안전 처리
- 깨진 한글 안내 문구 교정

### 2단계: 프론트 단독 진행 가능

- Figma 색상·서체·간격을 Android 리소스 토큰으로 정리
- 매니저 홈의 활성 세션 없음·있음 상태 시각 보정
- 자격 인증 상태별 카드 위계 정리
- 이력 목록과 읽기 전용 상세의 화면 책임 분리
- 로딩·빈 상태·오류·권한 거부 화면의 공통 컴포넌트화

### 3단계: 서버·제품 계약 필요

- 매니저 요청 목록·상세·self-accept
- 단계 2의 로비·진료과 checkpoint
- 대기번호와 기초 측정 구조화 필드
- 채팅의 서버 기반 시스템 이벤트

### 3.5단계: 코드 준비 후 통합 검증 필요

- 선택 결제 증빙 0~1개와 선택 처방 이미지 0~3개 업로드·교체·삭제
- `CARE_ENDED`와 최종 `COMPLETED` 분리, 최초 종료 시각과 중복 요청 복구
- 선택 매니저 일지 최대 300자와 리포트 실패 재시도
- V18 개발 DB 적용, Preview 배포와 실기기 재시작·네트워크 실패 검증

### 4단계: 통합 검증

- 단계 snapshot이 있는 테스트 세션으로 1~13 전환 확인
- 프로세스 종료·재실행 뒤 현재 단계 복구 확인
- 카카오맵 이동·복귀와 미설치 fallback 확인
- 권한 허용·거부·다시 묻지 않음 상태 확인
- Figma MCP 한도 복구 뒤 화면별 픽셀 비교

## 완료 기준

- 사용자는 현재 상태에서 가능한 주요 행동을 한 화면에서 하나만 명확히 확인한다.
- 작동하지 않는 CTA나 가짜 성공 상태가 운영 화면에 없다.
- Figma의 화면 위계를 따르되 Android 권한 정책과 서버 진행 판정을 우회하지 않는다.
- 활성 세션 유무, 심사 상태, 가이드 준비 상태가 앱 재실행 뒤에도 서버 값으로 복원된다.
- 알려진 13개 `stepCode`와 미지원 코드가 서로 다른 안전한 화면 영역으로 렌더링된다.
- 화면별 미구현 기능은 프론트·서버·제품 결정 중 어느 책임인지 문서와 Issue에서 추적된다.

## 남은 검증과 팀 요청

| 요청 대상 | 필요한 내용 | 확보되면 가능한 검증 |
| --- | --- | --- |

| 백엔드·앱 | V18 개발 적용과 테스트 세션 | 가이드 8·10·12·13 실제 업로드·종료·재시도 검증 |

현재 실기기에서는 Core API 연결, 매니저 홈, 가이드 진입과 `GUIDE_NOT_READY` 화면을 확인했다. 준비된 테스트 세션이 없으므로 가이드 1~13의 실제 저장·진행 결과는 완료로 기록하지 않는다.

## 리포트 완료 경계 판단 기록

- 작업 목적: 단계 계약이 깨진 세션의 리포트 제출과 정상 제출 뒤의 거짓 오류 표시를 막는다.
- 선택한 방식: 앱 CTA는 서버 판정에 따라 `ADVANCE`면 다음 단계, `LAST_STEP`이면 리포트 제출, 그 외에는 비활성화한다. 초안 저장 계약이 없는 리포트 입력 영역은 `LAST_STEP`에서만 표시하며, Core API도 검증된 `LAST_STEP`에서만 완료를 허용한다. 제출 성공 결과는 활성 세션 재조회와 분리한다.
- 대안: 앱 버튼만 비활성화하거나 제출 뒤 완료된 세션을 다시 조회하는 방식은 직접 API 호출과 활성 세션 필터를 안전하게 처리하지 못해 제외했다.
- 선택 이유: 현재 MVP에서도 세션 완료는 되돌리기 어려운 상태 변경이므로 화면과 서버의 이중 검증이 필요하다.
- 리스크: 리포트 제출 후 가이드 화면에 머물지 않고 매니저 홈으로 이동하므로, 완료 리포트 수정은 이력 화면의 별도 정책으로 제공해야 한다.
