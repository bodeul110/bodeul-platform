# 기획·디자인·구현 기준

기준일: 2026-09-27

## 작업 목적

Notion, Figma, 저장소 문서가 서로 다른 시점의 내용을 담고 있어 질문의 성격에 따라 기준을 분리한다. 한 자료를 모든 판단의 최상위에 두지 않고 제품, 디자인, 구현, 기술 계약의 책임을 명확히 한다.

## 기준 체계

| 확인할 내용 | 우선 기준 | 보조 기준 | 기준으로 쓰지 않는 것 |
| --- | --- | --- | --- |
| MVP 범위와 제품 의도 | 최신 Notion MVP 명세와 날짜·답변자가 확인되는 기획 결정 | 화면별 상세 명세, 내부 테스트의 사용성 의견 | 테스트 화면의 번호·기능을 새 요구로 자동 승격하거나 Figma 화면만으로 기능 확정 |
| 개인정보·동의·환불 등 운영 정책 | 확정자·확정일이 있는 기획 결정과 실제 법률 검토 결과 | Notion `개발 정책 관련 내용`, `보들 개인정보·민감정보·서류 보유기간 및 파기정책 v1.0` | 화면 예시 문구, 답변자·확정일이 없는 작업 메모 |
| 화면 구조와 시각 위계 | Figma `보들 MVP`의 `Page 1` | Notion 화면별 명세, 이전 `보들 가이드` 비교 기록 | 과거 PNG·ZIP export |
| 현재 구현 상태 | 저장소 코드, 자동화 검사, 실기기·배포 검증 기록 | `docs/status/implementation-status.md` | Notion의 `실제 구현` 표기 |
| 서버·DB·권한·API 계약 | `docs/architecture/`, Flyway migration, 서버 코드 | 관련 운영·검증 보고서 | Notion에 남은 Firestore 경로와 개발 제안 |
| 작업 추적 | GitHub Issue·PR·Project | Notion 회의 메모 | 완료 근거가 없는 체크 표시 |

| `보들 MVP 화면별 상세 개발 명세서 v2.2` | 화면 입력, 검증, 예외와 다음 화면 참고 | 최신 기획 답변과 이 문서의 반영 기록을 먼저 확인한다. `2026-08-30 현재 기준`과 아래에 남은 Firestore·Functions 중심 기술안, `실제 구현` 표기는 이후 결정이나 현재 코드·검증을 대체하지 않는다. |
| `보들 보호자↔매니저 동행 채팅 기능 명세서 v1.0` | 시스템 이벤트 중심 동행방의 제품 의도 | 참여자, 첨부, 보관 정책은 현재 구현과 운영 문서를 우선한다. |
| `보들 출시 전 법률 체크리스트 v1.0` | 출시 전 정책 게이트 | 법률 자문 결과가 아니며 확정된 정책과 구분한다. |
| `보들 플랫폼 기능설명서` | 초기 기능 배경과 전체 범위 | 최신 MVP 범위보다 우선하지 않는다. |

MVP 문서끼리 내용이 다르면 해당 항목의 최신 확정 답변과 반영 기록을 확인한다. 편집 시각만으로 옛 기능을 복원하거나, 내부 테스트 의견으로 최신 MVP 범위를 바꾸지 않는다.

2026-08-11 법률 검토 의견서는 서비스의 법적 위험과 필수 통제를 설명하는 조건부 자문이다. 기획의 계약 구조, 보관기간 숫자, 대리권 증빙, 위치정보 신고 여부를 대신 확정하지 않는다. 공개 저장소에는 원본을 올리지 않고 [2026-08-25 정책·법률 정합성 점검](../reports/notion-policy-legal-alignment-2026-08-25.md)에 공개 가능한 결론과 미회신 추가질의만 기록한다.

## Figma의 역할

- 기준 파일은 `보들 MVP`, file key `NX07k3Tu4cLc6YgAV82RXp`이다.
- 기준 페이지는 `Page 1`, node `0:1`이다. 2026-09-21 연결된 Figma에서 화면 메타데이터를 다시 확인했다.
- 이전 `보들 가이드`의 `Page 2(460:2)`는 과거 비교 자료다. 새 MVP 파일과 충돌하면 현행 제품 정책과 새 화면을 우선한다.
- 화면 배치, 정보 위계, CTA 위치, 상태별 시각 표현을 판단할 때 사용한다.
- 권한 필수 여부, 인증 제공자 활성화, 데이터 저장소, 매칭 규칙, 결제·환불 정책은 Figma 문구만으로 확정하지 않는다.
- 현재 화면과 코드의 대응은 [Figma MVP 구현 매핑](../design/figma-mvp-implementation-map-2026-08-29.md), 이전 파일의 기록은 [이전 Figma 화면 지도](../design/figma-current-screen-map.md)에 정리한다.

## 최근 원본 확인

2026-09-27 로그인된 Notion 브라우저에서 최소 MVP, 통합본 v1.1, 상세 명세 v2.2, 개발 정책과 내부 테스트 문서를 대조했다. 사용자용 제품 범위는 최신 MVP, 내부 테스트는 참고·고려 자료로 정리한다. 9월 9일 기획 답변의 보호자 예약·비식별 STT 내부 개발·관리자 보안 기준은 유지한다.

`내부테스트 2`에 메모 가독성, 단계 번호, 리포트 이동, 병원명·지도, 예약 후 하단 메뉴 잘림이 추가됐다. `지도는 이야기후 결정`과 STT 추가 논의 메모는 확정된 기능 변경으로 보지 않는다. 캡처의 7단계 표시를 현재 MVP의 13단계에 그대로 적용하지 않으며 [9월 27일 대조 기록](../reports/notion-mvp-feedback-triage-2026-09-27.md)에 이슈·PR 대응을 남긴다. 이번에는 Figma·법률 원본·운영 상태·실기기를 새로 검증하지 않았다.

2026-09-24 Notion 커넥터 조회는 `401 unauthorized / API token is invalid`로 실패했다. 무료 플랜이 원인이라는 근거는 아니다. 당시 GitHub·코드·개발 API 확인 범위와 과거 실기기 증적은 [9월 24일 기록](../reports/issue-sync-2026-09-24.md)에 보존한다.

2026-09-26에는 사용자가 로그인한 Codex 브라우저에서 정책 본문·표시된 전체 토론 패널, 내부 앱 피드백, MVP 통합본, 상세 명세의 표시된 본문, 보유기간 정책을 직접 읽었다. 당시 확인한 기획 답변의 최신 날짜는 9월 9일이고 `내부테스트 2`에는 제목만 있었다. 브라우저 열람 성공을 커넥터 인증 복구로 표현하지 않는다. 당시 상세 명세의 접힌 항목 전체와 Figma는 재확인하지 않았다.

구형 상봉번호·사진 안내·STT 전면 보류 같은 설명은 최신 기획 결정과 구분했다. [9월 26일 대조 결과](../reports/notion-browser-alignment-2026-09-26.md)에서 확인한 신규 40,000원 목표와 기본요금 69,000원 구현 차이는 [9월 28일 요금 변경](../reports/issue-27-mvp-price-2026-09-28.md)으로 보완했다. 기존 예약 금액은 유지하며 #27의 개별 기한·실제 입금 검증은 남는다. 첨부 영상이 있다는 사실만으로 사용 권리·비식별 검수·게시 승인을 완료로 보지 않는다.

## 충돌 해결 순서

1. 같은 제품 정책끼리 충돌하면 확정자와 확정일이 기록된 최신 결정을 따른다. 답변만 있고 승인 정보가 없으면 확정으로 올리지 않는다.
2. 제품 정책과 Figma가 충돌하면 정책을 유지하고 Figma 문구·화면을 수정 대상으로 기록한다.
   내부 테스트가 MVP와 충돌하는 경우에도 최신 MVP를 유지하고, 피드백은 재현 확인 또는 후속 제안으로 분류한다.
3. Notion 기술 제안과 저장소 기술 계약이 충돌하면 저장소의 코드·migration·검증 기록을 따른다.
4. `구현 완료` 표기가 충돌하면 실제 코드 경로와 테스트·배포·실기기 증거가 있는 쪽만 완료로 본다.
5. 확정 근거가 없어도 법률·보안·민감정보·비가역 삭제·금전·외부 호환성에 영향을 주지 않고 코드나 설정으로 되돌릴 수 있는 제품 기본값은 개발팀이 정해 구현할 수 있다. 임시라는 이유만으로 이슈를 열어 두지 않으며 변경 요구가 생기면 새 변경 작업으로 처리한다. 세부 판정은 [MVP 정책 기본값 결정 경계](mvp-policy-default-boundary.md)를 따른다.
6. Notion의 마지막 편집 시각이 직전 저장소 정합성 점검보다 늦으면 변경 항목을 다시 대조한 뒤 관련 Issue와 문서를 갱신한다.
7. 보유기간이나 수집 범위가 충돌하면 최소수집·목적달성 후 파기·현재 검증된 삭제 계약을 함께 비교해 보수적인 단일 기준을 정한다. 실제 production 삭제 apply는 처리방침, 책임자, 복원 검증이 끝날 때까지 비활성으로 둔다.
8. 법률 검토가 필요한 민감수집·위치·권한·결제는 근거가 없으면 수집하지 않거나 기능을 끈다. 코드 골격과 합성 데이터 검증은 진행할 수 있지만 실제 사용자 활성화와 권한 확대는 별도 게이트를 통과해야 한다.

## 2026-09-09 기획 답변 반영

2026-09-13에 Notion `개발 정책 관련 내용`의 새 답변을 기준으로 다음 변경을 채택했다. 세부 범위는 [MVP 범위](mvp-scope.md)와 [Notion 제품 기준 정합성](notion-product-alignment.md)에 반영한다.

- 보호자 예약 생성과 환자 동의 범위 내 진행·최종 리포트 조회는 [#419](https://github.com/bodeul110/Bodeul/issues/419)에서 기존 앱·Core API 계약과의 차이를 구현한다. 공통 하단 탭은 유지하고 다중 환자 관리 UI와 복잡한 딥링크 예외는 MVP에서 제외한다.
- 네이버 클라우드 STT 내부 연동, 녹음 시작·정지·정지 후 자동 저장은 [#420](https://github.com/bodeul110/Bodeul/issues/420)의 개발 범위다. 실제 환자 데이터를 쓰지 않는 내부 검증과 운영 활성화는 분리한다. OCR·AI 요약·최종 리포트 자동 반영은 이번 범위가 아니다.
- 관리자 역할 승인, MFA·유휴 로그아웃, 임시 권한 회수·긴급 접근, 감사기록 1년과 접근권한 점검은 [#134](https://github.com/bodeul110/Bodeul/issues/134)의 출시 검증 기준으로 구체화한다. 정책 채택과 실제 설정·검증 완료를 구분한다.

완료된 과거 이슈는 그대로 두고 새 요구에 필요한 차이만 새 작업으로 추적한다. 보안·동의 경계를 완화하거나 미검증 기능을 완료로 표기하지 않는다.

## 갱신 절차

1. 기획 변경은 Notion의 기준 명세와 관련 GitHub Issue에 함께 남긴다.
2. 화면 변경은 Figma frame 이름과 prototype 연결을 정리한 뒤 관련 Issue에 node ID를 남긴다.
3. 기술 계약 변경은 저장소 코드와 `docs/architecture/`를 같은 PR에서 수정한다.
4. 구현이 끝나면 `docs/status/implementation-status.md`에 실제 검증 결과를 기록한다.
5. 과거 PDF, PNG, ZIP은 날짜가 있는 스냅샷으로만 보관하고 현재 기준 색인에서 제외한다.

## 선택 근거

현재 프로젝트는 기획 문서보다 구현이 앞선 영역과 Figma가 구현보다 앞선 영역이 함께 있다. 자료 하나를 최상위 기준으로 두면 PostgreSQL 전환을 Firestore로 되돌리거나, 시안 속 AI·OCR를 완료 기능으로 오해할 수 있다. 질문별 기준을 분리하면 제품 의도는 유지하면서 검증된 기술 계약을 보호할 수 있다.

## 대안과 리스크

- Notion을 모든 내용의 단일 기준으로 쓰면 기획 접근성은 좋아지지만 코드와 함께 검증되는 API·DB 계약이 쉽게 낡는다.
- 저장소만 기준으로 쓰면 기술 근거는 강하지만 기획·법률 결정과 최신 화면 의도를 놓칠 수 있다.
- 분리 기준은 갱신 지점이 늘어나는 단점이 있다. 이를 줄이기 위해 변경마다 Issue와 이 문서의 갱신 절차를 따른다.
