# Notion 제품 기준 정합성

기준일: 2026-09-27

이번 갱신은 최신 Notion MVP·개발 정책·내부 테스트와 메인 저장소 및 관련 GitHub 이슈·PR을 대조한 것이다. Figma·법률 원본·관리자 웹 전체·서버·DB·실기기의 종단 검증을 새로 수행한 기록은 아니다. 이전 날짜의 대조 기록과 이번 확인 범위를 구분한다.

## 확인 범위

이전 대조 범위와 날짜는 다음 문단에 보존한다. 9월 27일 새로 읽은 원문은 최소 MVP·통합본 v1.1·상세 명세 v2.2의 전체 흐름·요약표, 개발 정책과 내부 테스트이며 [대조 기록](../reports/notion-mvp-feedback-triage-2026-09-27.md)에 구분했다.

Notion의 MVP 통합본 v1.1, 화면별 상세 명세 v2.2, 동행 채팅 명세 v1.0, 출시 전 법률 체크리스트 v1.0, `개발 정책 관련 내용`, 보유기간 및 파기정책 v1.0을 현재 저장소 구현과 대조했다. 2026-08-25에는 기획 답변과 2026-08-11 법률 검토 의견서를, 2026-09-01에는 위치·결제·가이드 2 후속 기획 답변을 다시 확인했다. 2026-09-03에는 기존 매니저 위치 경로의 production 차단 경계를 코드 변경 기준으로 갱신했다. 2026-09-13에는 `개발 정책 관련 내용`의 2026-09-09 답변에 맞춰 보호자 예약, STT 내부 개발과 관리자 보안 기준을 갱신했다. 같은 날 `보들 앱 화면 피드백` 원문과 예시 이미지도 내부 테스트 결과로 대조하고 후속 이슈에 연결했다. 이번 갱신에서 배포·실기기·DB 상태를 직접 재검증한 것은 아니며 기존 구현 증적과 팀의 테스트 의견을 구분해 유지한다. 비공개 URL, 페이지 ID, 계정 정보, 개인정보와 법률 문서 원본은 이 공개 저장소에 기록하지 않는다.

## 충돌 판정 기준

- 제품 목표가 충돌하면 날짜와 답변자가 확인되는 최신 기획 답변을 기존 기획 문서와 Figma보다 우선한다.
- 최신 Notion MVP가 제품 범위의 기준이다. 내부 테스트는 결함·사용성 개선의 참고 자료로 고려하며 화면 번호·기능 요청을 새 MVP 요구로 자동 승격하지 않는다.
- 법률·보안·외부 서비스 약관과 이미 배포된 데이터 계약은 기획 답변만으로 완화하지 않는다. 실제 수집·결제·삭제·권한 확대는 별도 운영 게이트를 통과해야 한다.
- 현재 구현 여부는 저장소의 코드·API·DB migration과 검증 기록으로 판단한다. 기획 답변이나 Figma 화면이 있다는 이유로 구현 완료로 표시하지 않는다.
- 개발자 제안은 위 기준에 답이 없고 되돌릴 수 있는 MVP 기본값에만 사용한다.

## 현재 제품 흐름

1. 첫 화면과 권한 안내를 거쳐 환자·보호자 또는 매니저 역할을 선택한다.
2. 매니저는 자격 서류 제출과 승인 단계를 거친다.
3. 성인 환자가 병원, 일정, 건강·이동 정보를 입력해 동행을 요청한다. 보호자의 환자 대상 예약 생성과 환자 동의 범위 내 진행·최종 리포트 조회도 제품 목표로 포함한다. 예약 생성 사실만으로 정보 전체 접근권한을 주지 않으며, 새 구현 차이는 [#419](https://github.com/bodeul110/Bodeul/issues/419)에서 추적한다.
4. 관리자가 승인된 매니저 한 명을 배정한다. 승인 매니저의 공개 일감 목록과 선착순 수락은 MVP에서 제외한다.
5. 매칭 이후 매니저는 동행 가이드를 진행하고 환자·보호자는 진행 상태를 확인한다.
6. 환자·배정 매니저와 `CHAT` 정보공유 동의가 유효한 보호자는 직접 채팅하고 주요 상태 알림을 받는다. 보호자의 첨부 이용에는 `CHAT + ATTACHMENT`가 모두 필요하다. 시스템 이벤트 중심 동행방은 과거 제안으로 분류한다.
7. 현장 종료와 최대 300자 동행 일지·최종 리포트 흐름을 구분한다. 후기는 UI만 포함하며 후기 작성·저장과 실제 정산을 제공 완료로 설명하지 않는다. 별도 SOS·자동 연락·사고 기록은 MVP에서 제공하지 않는다.

최신 Notion MVP의 목표는 동행 가이드 1~13 흐름이다. 현재 서버·앱은 병원 가이드 snapshot의 `stepCode`·순서를 사용하므로 기존 7단계 세션까지 고정 숫자로 재배열하지 않는다. 단계별 사용자용 범위는 [MVP 범위](mvp-scope.md)의 C06~C13 표를 따른다.

## 2026-09-09 기획 답변의 적용 범위

아래는 2026-09-13에 채택한 최신 제품·운영 기준이다. 앞선 문서의 보호자 예약 전면 제외와 STT 개발 전면 보류 문구보다 우선한다. 정책을 채택했다는 사실은 구현 또는 실제 운영 설정 완료를 뜻하지 않는다.

## MVP 기본값 결정 원칙

- 기존 기획 답변과 확정 정책은 그대로 유지한다.
- 법률·보안·민감정보·비가역 삭제·금전·외부 호환성과 충돌하지 않고 코드나 설정으로 되돌릴 수 있는 값은 환경과 무관하게 개발팀이 정할 수 있다.
- 선택 이유와 변경 위치를 Issue 또는 PR에 기록하되 임시라는 이유만으로 이슈를 열어 두지 않는다.
- 실제 개인정보의 수집·보관·삭제, 권한 확대, 비용 발생, 법정 의무 변경은 임시값 위임 대상이 아니다.
- 위험한 미결 항목은 비활성, dry-run 또는 fail-closed를 기본으로 한다.

개발팀 기본값 위임의 이전 근거는 [2026-08-28 MVP 정책값 경계 점검](../reports/notion-policy-team-response-alignment-2026-08-28.md), 현재 충돌 해소 결과는 [2026-08-30 Notion 정책 충돌 해소 결과](../reports/notion-policy-conflict-resolution-2026-08-30.md)에 기록한다.

## 확정해서 유지할 내용

- 예약·세션·채팅·읽음·리포트·후속 처리의 쓰기 원본은 PostgreSQL이다. 기존 매니저 위치 경로는 기본 `OFF`이고 release·production에서는 활성화하지 않는다. 환자 GPS 1분 공유는 제품 목표지만 별도 경로를 구현하고 production 게이트를 통과하기 전에는 수집·공유하지 않는다.
- 환자·보호자·매니저 앱은 Spring Core API를 거친다.
- 관리자 웹은 별도 Next.js 서버를 통해 같은 PostgreSQL을 본다.
- Firebase는 Auth, App Check, FCM, Storage와 결합 Functions에 사용한다.
- 인증 프로필·지원·매니저 서류 심사 메타데이터 일부는 전환 기간 Firestore에 남아 있고, 자격 증빙과 세션 첨부 파일 원본은 Firebase Storage에 둔다. 현재 자격 서류 심사 상태는 Firestore 계약을 유지한다. PostgreSQL의 관리자 RBAC·감사와 outbox를 함께 사용하며, 이를 심사 도메인 전체 이전 완료로 표시하지 않는다.
- Realtime은 권위 있는 데이터 원본이 아니라 PostgreSQL 커밋 알림이다.
- OCR, 진료 녹음, STT, AI 요약은 시안이나 문서가 있어도 현재 완료 기능으로 표시하지 않는다.
- 음성·STT 전면 제외와 `CLOVA Speech STT → Codex 재가공 실제 구현` 표기는 9월 9일의 STT 내부 개발 범위로 대체한다. 기존 #30의 전체 AI 리포트 보류와 새 #420을 구분하며, 실제 연동 증거 전에는 완료로 표시하지 않는다.

## 문서 정리 판단

- Notion은 제품 의도와 미결 정책의 기준으로 유지한다.
- Notion의 Firestore 컬렉션명, Functions 처리와 구현 완료 표기는 현재 코드의 기술 사실을 대체하지 않는다.
- Notion 문서의 마지막 편집 시각이 저장소 정합성 점검 이후라면 변경된 항목을 다시 대조한다. 되돌릴 수 있는 기본값과 별도 production 게이트는 [MVP 정책 기본값 결정 경계](mvp-policy-default-boundary.md)에 따라 구분한다.
- 오래된 로컬 기능설명서 PDF는 초기 범위 스냅샷으로 낮춘다.
- 구현 상태는 [현재 구현 상태](../status/implementation-status.md), 기술 구조는 [목표 인프라 구조](../architecture/target-infrastructure.md)를 따른다.
