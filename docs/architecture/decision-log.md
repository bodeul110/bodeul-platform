# 설계 판단 기록 규칙

기준일: 2026-06-25

초기에는 빠른 구현을 우선했기 때문에 모든 선택 근거가 사전에 정리되지는 않았다.
현재는 구현된 구조를 기준으로 선택 이유, 대안, 단점, 전환 조건을 정리하고 있다.

이 문서는 앞으로 기능 개발, 구조 변경, 운영 설정 변경을 할 때 팀이 최소한으로 남겨야 하는 판단 기록 형식이다. 목적은 처음부터 완벽하게 설계한 것처럼 보이게 하는 것이 아니라, 현재 구조를 이해하고 팀의 판단으로 설명할 수 있게 만드는 것이다.

## 기본 원칙

- 기능 개발 전에 “왜 이 작업을 하는지”를 한 줄이라도 쓴다.
- “AI가 제안했다”는 선택 이유가 될 수 없다. AI 제안은 검토 대상이고, 최종 판단은 팀이 책임진다.
- 선택 근거는 항상 현재 팀 규모, MVP 단계, 운영 부담과 연결해서 설명한다.
- 대안과 리스크를 짧게라도 남긴다. 당장 선택하지 않은 이유와 나중에 바꿀 조건이 중요하다.

## PR과 작업 문서 기준

일반 PR은 아래처럼 짧게 쓴다. 작업과 무관한 빈 구획은 삭제한다.

```markdown
## 배경

무엇을 해결하려는 작업인가?

## 변경 내용

무엇이 달라졌는가?

## 확인

실제로 무엇을 실행하거나 확인했는가?

## 참고할 점

리뷰가 필요한 판단, 리스크, 후속 작업이 있는가?
```

설계, 보안, 인프라처럼 선택 자체가 중요한 작업은 본문이나 별도 문서에 선택한 방식, 대안, 선택 이유, 리스크를 덧붙인다. 모든 PR에 같은 장문 형식을 반복하지 않는다.

## 좋은 설명 기준

나쁜 설명:

> AI가 이렇게 하라고 해서 했습니다.

좋은 설명:

> AI가 제안한 구조를 검토했고, Activity에 로직이 몰리는 문제를 줄이기 위해 Coordinator와 Repository로 역할을 나누는 방식을 유지하기로 했다. 다만 파일 수가 많아지는 단점이 있어 화면별 구조 문서를 추가했다.

## 현재 규모와 연결하는 표현

- 현재 MVP에서는 Firebase Auth와 FCM을 유지해 인증과 알림 전환 위험을 줄인다.
- 운영 DB는 관계형 조회와 감사 이력을 위해 Supabase PostgreSQL로 단계 전환한다.
- 관리자 서버와 Spring Core API를 분리하되 서버가 다른 서버를 거쳐 DB로 가는 중복 경로는 만들지 않는다.
- 현재 매칭은 추천 모델이 아니라 규칙 기반 운영 로직으로 보고, 데이터가 충분히 쌓인 뒤 추천 모델을 검토한다.

## 2026-09-03 MVP SOS·사고 대응 비활성

- 작업 목적: 확정된 비의료 동행 MVP 범위와 남아 있던 SOS·사고 기록 기능을 일치시킨다.
- 선택한 방식: 사용자·매니저·관리자의 신규 SOS 실행과 쓰기를 제거하고 Core API에서 신규 escalation 요청을 거부하되 기존 필드와 파서는 읽기 호환으로 유지한다.
- 대안: 안내만 숨기기, 기존 데이터 즉시 삭제, 사고 중단·자동 연락까지 이번 범위에 추가하기를 검토했다.
- 선택 이유: 현재 MVP에는 사고 대응 책임·연락·보험 기준이 없고, 데이터 삭제는 구버전 호환을 깨뜨리므로 신규 쓰기만 fail-closed하는 것이 안전하다.
- 리스크: 과거 값은 내부 응답에 남는다. 향후 기능을 다시 도입하려면 연락 순서·응답시간·보관·법률·보험 기준을 새로 승인해야 한다.

상세 기준은 [MVP SOS·사고 대응 비활성 경계](mvp-accident-response-boundary.md)를 따른다.

## 2026-09-15 매니저 동행 가이드 문진 준비 화면

- 작업 목적: 매니저 가이드의 `PRE_CONSULTATION` 범용 카드 구성을 피그마 MVP의 보호자 요청·체크리스트·검토 완료 흐름에 맞춘다.
- 선택한 방식: 예약 요청의 실제 주의사항·약물 요약을 읽고, 체크리스트 세 항목을 모두 확인한 경우에만 기존 서버의 단일 `preConsultationConfirmed` 필드를 저장한다. 이후 단계 이동은 서버의 진행 판정을 따른다.
- 대안: 피그마의 예시 인물·혈압약 문구를 그대로 표시하거나 체크별 완료 상태를 별도 API로 저장하는 방식을 검토했다.
- 선택 이유: 예시 데이터는 실제 요청으로 오인될 수 있고, 체크별 저장 계약은 현재 없으므로 프론트엔드 범위에서 전체 확인만 기존 계약에 연결한다.
- 리스크: 체크별 선택은 화면 임시 상태라 미완료 상태에서 화면을 다시 열면 복원되지 않는다. 독립적인 체크 이력이 필요해지면 백엔드 계약과 감사 기준을 먼저 합의해야 한다. 실제 서버 HTTP 500/503 때문에 종단 저장·이동 검증도 후속 확인이 필요하다.

자세한 데이터 대응은 [문진 준비 화면 구현 기록](../design/figma-manager-guide-pre-consultation-implementation-2026-09-15.md)을 따른다.

## 2026-09-19 매니저 상봉 단계 현재 위치 확인

- 작업 목적: 상봉 단계에서 매니저가 카카오 지도 위에 자신의 현재 위치를 확인할 수 있게 한다.
- 선택한 방식: 사용자가 버튼을 누를 때 전경 위치를 한 번만 읽어 앱 내부 지도에 표시하고, 좌표는 저장하거나 서버로 전송하지 않는다.
- 대안: 외부 카카오맵 앱으로 이동하거나 기존 실시간 위치 공유 기능을 다시 활성화하는 방식을 검토했다.
- 선택 이유: 앱 내부에 이미 카카오 지도 SDK가 있고, 일회성 로컬 표시는 MVP 요구를 충족하면서 개인정보·배터리·백엔드 계약 변경을 최소화한다.
- 리스크: 실내나 GPS 수신이 약한 환경에서는 마지막 위치가 표시되거나 위치 확인이 실패할 수 있다. 지속 공유가 필요해지면 동의, 보관, 수신자, 중단 기준을 먼저 확정해야 한다.

구현 범위와 검증 항목은 [현재 위치 확인 구현 기록](../design/manager-guide-current-location-implementation-2026-09-19.md)을 따른다.

## 2026-09-19 매니저 단계 메모 읽기 전용 조합

- 작업 목적: 동행 종료 직전에 앞 단계의 수동 기록을 다시 입력하지 않고 확인한다.
- 선택한 방식: 현재 세션 응답에 존재하는 5개 최신 원문을 단계 범위와 함께 읽기 전용으로 조합하고, 같은 원문은 한 번만 표시한다.
- 대안: 300자 최종 일지에 자동 복사하거나 기기에 원문을 캐시하는 방식을 검토했다.
- 선택 이유: 자동 복사는 잘림과 조용한 내용 변경을 만들고, 기기 캐시는 세션 혼합·민감정보 잔존·재진입 불일치를 만들 수 있다.
- 리스크: 공통 단일 필드는 단계별 과거값을 보존하지 않으며 `CARE_ENDED` 뒤 서버가 원문을 마스킹한다. 현재는 종료 전에만 표시하고, 종료 후 재진입 표시는 별도 최소 조회 계약과 보안 검토가 필요하다.

필드 대응과 남은 서버 조건은 [단계 메모 모아보기 설계](../design/manager-guide-step-memo-summary-2026-09-19.md)를 따른다.

## 2026-09-20 매니저 기초 측정값의 기존 메모 계약 재사용

- 작업 목적: `VITALS_CHECK`의 범용 현장 메모를 Figma MVP의 혈압·심박수·체중 입력 화면으로 구체화한다.
- 선택한 방식: 세 측정값을 선택 입력으로 받고 단위를 포함한 구조화 텍스트로 만든 뒤 기존 `fieldPhotoNote`에 저장한다. 저장 성공과 세션·단계 불변을 확인한 경우에만 다음 단계로 이동한다.
- 대안: 화면만 먼저 노출하거나 앱 로컬에만 값을 저장하거나 승인되지 않은 서버 필드를 추가하는 방식을 검토했다.
- 선택 이유: 화면만 노출하면 값이 사라지고 로컬 저장은 기기·세션 간 불일치를 만들며, 서버 필드 추가는 프론트엔드 작업 범위를 벗어난다. 현재 쓰기 가능한 계약을 명시적으로 재사용하는 것이 MVP에서 가장 작은 변경이다.
- 리스크: `fieldPhotoNote`는 여러 단계가 공유하는 최신값이라 단계별 이력을 보존하지 못한다. 구조화 조회나 의료적 정상 범위 판정이 필요하면 별도 DTO와 보관·권한 기준을 먼저 합의해야 한다.

구현·검증 범위는 [기초 측정 화면 구현 기록](../design/manager-guide-vitals-implementation-2026-09-20.md)을 따른다.

## 2026-09-20 매니저 처방 이미지는 기존 선택 첨부 계약 유지

- 작업 목적: `PRESCRIPTION_DOCUMENTS`의 범용 첨부 UI를 Figma MVP의 처방 자료 화면 위계에 맞춘다.
- 선택한 방식: Figma의 안내·선택 카드 구조를 적용하되 기존 시스템 문서 선택기와 `PRESCRIPTION_IMAGE` 교체·삭제 API를 그대로 사용하고, JPEG·PNG 최대 3개·파일당 10MiB·선택 입력이라는 실제 계약을 화면에 표시한다.
- 대안: Figma 문구대로 카메라 전용 촬영과 영수증 OCR·AI 분석을 추가하거나 첨부를 필수로 바꾸는 방식을 검토했다.
- 선택 이유: 카메라·OCR·필수 입력은 현재 서버 계약과 제품 승인 범위를 벗어난다. 이미 검증된 문서 선택기와 선택 첨부 계약을 유지하면 가짜 완료 상태나 저장되지 않는 기능을 만들지 않고 시각 구조만 개선할 수 있다.
- 리스크: debug 단계 미리보기로 로컬 선택·교체·삭제는 검증할 수 있지만, 실제 Core API 업로드와 앱 재진입 뒤 보존을 포함한 종단 검증에는 `PRESCRIPTION_DOCUMENTS` 개발 세션이 필요하다. 카메라 직접 촬영이나 OCR이 필요해지면 권한, 원본 보관, 실패 재시도와 서버 처리 계약을 먼저 정해야 한다.

구현 차이와 검증 범위는 [처방 이미지 화면 구현 기록](../design/figma-manager-guide-prescription-implementation-2026-09-20.md)을 따른다.

- 대안: 운영 다음 버튼 강제 활성화, Preview DB fixture 상시 사용, 두 번째 launcher 아이콘을 검토했다.
- 선택 이유: release에 서버 판정 우회를 남기지 않으면서 인프라 권한 없이 모든 단계를 즉시 재현할 수 있고, 기존 launcher 자동화도 유지한다.
- 리스크: 로컬 미리보기는 실제 인가·DB·업로드·realtime 연동을 검증하지 않으며, 서버 단계 계약이 바뀌면 debug 카탈로그를 같이 갱신해야 한다.

진입 방법과 경계는 [매니저 가이드 debug 미리보기](../design/manager-guide-debug-preview.md)를 따른다.

## 2026-09-26 매니저 진료 보조 화면의 운영·debug 경계

- 작업 목적: `CONSULTATION_SUPPORT`를 Figma 진료 보조 화면에 맞추면서 실제 녹음·STT가 구현된 것처럼 오해할 수 있는 표현을 차단한다.
- 선택한 방식: 운영 앱에는 기존 `guardianUpdate`와 `fieldPhotoNote` 수동 입력·개별 저장만 제공하고, 녹음 버튼과 타이머는 실제 오디오를 만들지 않는 debug 전용 로컬 상태 미리보기로 제한한다. Figma node `8:1735` 내부의 잘못된 `STEP 03`은 서버 snapshot의 동적 순번으로 교정한다. 미저장 초안은 `SavedStateHandle`, View hierarchy 자동 상태나 영구 저장소에 남기지 않고 회전 동안 유지되는 ViewModel 메모리에만 보관하며, 저장은 기대 세션 ID와 `CONSULTATION_SUPPORT` 단계를 다시 확인하고 단일 mutation gate로 직렬화한다. 미저장 내용은 다음 단계 CTA뿐 아니라 툴바·시스템 뒤로가기와 하단 내비게이션 이탈 확인으로 보호하고, 버리기 선택 시 서버 기준값 복원과 초안 제거를 먼저 수행한다. 미저장 입력의 저장 mutation 중에는 이탈을 막아 진행 중인 저장과 버리기가 경합하지 않게 한다.
- 대안: 운영 화면에 비활성 녹음 UI를 먼저 노출하거나, 프론트에서 음성 파일만 로컬 저장하거나, 예시 질문 네 개를 고정 데이터로 표시하는 방식을 검토했다.
- 선택 이유: 현재 MVP 서버에는 오디오 업로드·보관·STT 결과 계약이 없고 Figma 예시는 실제 환자 데이터가 아니다. 이미 쓰기 가능한 두 필드만 연결하면 저장되지 않는 기능과 가짜 기록을 만들지 않으면서 진료 단계 화면을 검증할 수 있다.
- 리스크: 두 필드는 단계별 이력이 아니라 세션의 최신 값이므로 이후 저장으로 교체될 수 있다. 메모리 초안은 화면 회전에는 남지만 프로세스 종료나 사용자가 버리기를 확인한 이탈에서는 복구되지 않는다. 단일 mutation gate는 앱 내부의 중복 요청을 막지만 다른 기기나 서버의 동시 변경 자체를 없애지는 않으므로 세션·단계 불일치는 저장을 거부하고 재조회해야 한다. debug 미리보기는 마이크 권한, 파일, 네트워크와 제공자 품질을 검증하지 않으며 실제 Naver STT와 오디오 저장은 Issue #420에서 별도로 구현해야 한다.

구현 범위와 미완료 경계는 [진료 보조 화면 구현 기록](../design/figma-manager-guide-consultation-implementation-2026-09-26.md)을 따른다.

## 2026-09-27 진료 요약 저장과 초안 보호

- 작업 목적: 진료 요약 저장 중 단계 전환과 미저장 메모 유실을 막는다.
- 선택한 방식: 기존 Core API의 기대 세션·단계 PATCH 계약과 단일 mutation gate를 사용한다. 초안은 ViewModel 메모리에서 회전 중에만 유지하고, 다음 단계·뒤로가기·하단 메뉴에서 저장 또는 버리기를 확인한다.
- 대안: 자동 저장이나 SavedStateHandle의 프로세스 복원 저장을 검토했다.
- 선택 이유: 현재 MVP에서는 기존 수동 저장 흐름을 유지하는 편이 의도하지 않은 기록 변경을 줄이고, 진료 메모를 기기 영구 상태에 남기지 않는다.
- 리스크: 프로세스 종료 시 미저장 초안은 사라진다. 서버의 공통 최신 메모 필드를 재사용하므로 단계별 이력을 추가하지 않으며, 관리자 웹과 서버 DTO·DB schema는 바꾸지 않는다.

## 2026-09-27 권한 없이 가능한 클라이언트 회귀 보완

- 작업 목적: 최신 Figma 화면과 서버 계약은 유지하면서 예약 내역 하단 탭, 데모 병원 표기, 동행 메모·복약 대조 가독성의 남은 회귀를 정리한다.
- 선택한 방식: 예약 내역 스크롤 콘텐츠와 하단 탭에 시스템 바·디스플레이 컷아웃 inset을 비누적 방식으로 적용하고, 샘플·debug 데이터의 병원명과 좌표를 `서울대학교병원` 기준으로 통일한다. 좌표가 없는 외부 지도 fallback 검색어는 병원명만 사용하며 앱 내부 좌표 검색의 병원명+진료과 fallback은 유지한다. 메모 입력값과 복약 대조 선택지는 최신 Figma의 진한 본문색 토큰을 명시한다.
- 대안: 모든 화면의 전역 테마를 바꾸거나 운영 예약 데이터를 특정 병원으로 고정하고, 지도 검색에서 진료과를 전부 제거하는 방식을 검토했다.
- 선택 이유: 전역 테마 변경은 무관한 화면의 회귀 위험이 있고 운영 데이터 하드코딩은 실제 예약을 훼손한다. 외부 fallback만 단순화하면 잘못된 장소 검색을 줄이면서 기존 좌표 탐색 정확도와 최신 화면 구조를 보존할 수 있다.
- 리스크: 병원명이 비어 있고 좌표도 없는 비정상 예약은 외부 지도 검색어가 비게 된다. STT·단계별 append-only 메모 이력·실제 서버 세션 검증은 별도 백엔드 계약과 환경 권한이 필요하므로 이번 변경에 포함하지 않는다.

## 2026-09-27 개발·운영 브랜치와 배포 경계

- 작업 목적: 기능 검증 중인 코드와 DB가 운영 배포 경로에 섞이지 않게 한다.
- 선택한 방식: 두 저장소에 `dev`를 두고 개발 배포는 `dev`, 운영 배포는 `master`로 제한한다. DB migration은 환경별 수동 승인 작업으로 유지하고 GitHub OIDC의 immutable subject에 인증 binding을 맞춘다.
- 대안: 모든 작업을 `master`와 수동 변수로 구분하거나 새 staging 프로젝트를 추가하는 방식을 검토했다.
- 선택 이유: 현재 MVP 규모에서는 기존 개발·운영 두 프로젝트를 분리 사용하는 것이 추가 서버·DB 비용 없이 실수 가능성과 운영 부담을 줄인다. 장기 브랜치 간 merge commit은 다음 출시에도 공통 이력을 보존한다.
- 리스크: 기존 기능 PR은 전환 중 `master`를 대상으로 남아 있을 수 있다. DB 스키마와 앱 배포는 별도 실행이므로 적용 순서와 복구 증거를 기록해야 하며, CI 통과만으로 실제 운영 연결 성공을 주장하지 않는다.

적용 순서와 결과는 [개발·운영 분리](../operations/dev-production-branch-transition-plan.md)를 따른다.

## 2026-09-27 앱·웹 환경 혼합 차단

- 작업 목적: 브랜치만 나누고 Firebase·DB 연결은 잘못 공유하는 사고를 빌드와 서버 연결 단계에서 막는다.
- 선택한 방식: Android의 Debug/Release Firebase 파일과 API·Realtime 속성을 분리하고, Vercel에서는 배포 환경별 Firebase·DB 프로젝트와 관리자 전용 role을 확인한다.
- 대안: 이름 표시 배지만 붙이거나 문서 점검에만 맡기는 방식을 검토했다.
- 선택 이유: 현재 두 환경의 식별자가 고정되어 있어 작은 allowlist와 자동 회귀 검사로 설정 실수를 빨리 발견할 수 있다. 새 dependency나 클라이언트 DB 비밀번호는 필요하지 않다.
- 리스크: 새 도메인·리전·프로젝트를 도입하면 allowlist도 검토해서 바꿔야 한다. CI placeholder 성공은 운영 인증·DB 연결 성공과 다르며, 검증되지 않은 운영 값으로 배포를 통과시키지 않는다.

## 2026-09-27 현재 문서와 과거 실행 기록의 분리

- 작업 목적: DB 일시정지·첫 배포 전·관리자 계정 등록만 완료라는 오래된 설명을 실제 개발·운영 분리 결과에 맞춘다.
- 선택한 방식: README는 프로젝트 소개를 유지하고 현재 운영 기준·아키텍처·상태 문서를 갱신한다. 날짜가 있는 과거 검증 보고서는 당시 사실을 보존하며 최신 실행 기록을 연결한다.
- 대안: 모든 과거 문서를 최신 상태로 덮어쓰거나 새 보고서 하나만 추가하는 방식을 검토했다.
- 선택 이유: 현재 MVP 규모에서도 검증 이력과 현재 접속 절차를 구분해야 반복 작업과 잘못된 출시 판단을 줄일 수 있다. Notion MVP가 제품 기준이고 내부 테스트는 개선 근거라는 기존 우선순위를 유지한다.
- 리스크: DB 연결·최초 관리자 TOTP 성공이 운영 업무·전체 MFA/App Check 강제를 보장하지 않는다. 재실행하지 않은 제공자 상태와 실기기 흐름은 확인 완료로 바꾸지 않는다.

## 2026-09-27 생성 승인과 예약 본문 결합

- 작업 목적: 같은 생성 요청 ID의 내용을 최초 저장 전에 바꾸어 환자가 보지 않은 예약을 만드는 판정 공백을 막는다.
- 선택한 방식: 기존 서버 생성 fingerprint를 승인 기록에 보관하고 최초 생성 판정에서 본문 일치를 검사한다. 본문 변경은 재승인을 요구하며 기존 insert 멱등성 검사도 유지한다.
- 대안: 요청 ID만 비교하거나 별도의 pending 요청 테이블을 추가하는 방식을 검토했다.
- 선택 이유: 현재 순수 판정 준비 단계에서는 기존 정규화 본문의 해시 계약을 재사용하면 DB migration 없이 범위를 고정할 수 있다. 별도 해시 규칙을 복제하지 않는다.
- 리스크: fingerprint는 서버가 검증한 본문에서 계산해야 하며 클라이언트 제공값을 신뢰하면 안 된다. 실제 API 연결 시 승인·철회·insert를 같은 트랜잭션에서 검사하는 경계는 여전히 필요하다.
