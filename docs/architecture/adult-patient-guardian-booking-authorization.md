# 성인 환자·보호자 예약 생성 승인 계약

기준일: 2026-09-27

상태: #419의 순수 Java 판정 코드와 자동 테스트 준비. **DB 저장·API 연결·Android 화면·환경 배포는 아직 없으며 보호자 예약 생성은 계속 403으로 차단한다.**

## 작업 목적

9월 9일 기획 답변에서 채택한 보호자 예약 생성을 기존 정보공유 동의와 분리한다. 현재 `guardian-sharing-consent`는 이미 존재하는 예약을 요구하므로, 이 동의만으로 예약 전 생성 권한을 판정하면 순환 의존이 생긴다. 현재 근거는 [9월 26일 원본 대조](../reports/notion-browser-alignment-2026-09-26.md), [9월 27일 MVP·내부 테스트 대조](../reports/notion-mvp-feedback-triage-2026-09-27.md), [기획 기준](../planning/source-of-truth.md)과 [#419](https://github.com/bodeul110/bodeul-platform/issues/419)다. 9월 24일 인증 오류로 9월 21일 기록을 사용한 것은 초안 작성 당시의 경위이며 현재 미확인 상태를 뜻하지 않는다. 이번 리뷰 수정에서는 저장소에 남은 대조 기록을 확인했으며 Notion 원문을 새로 조회하지 않았다.

## 선택한 방식

`AdultPatientGuardianBookingPolicy`는 기존 정보공유 판정기와 같은 순수 Java 구조를 사용하되 요청별 단일 `ApprovalState`, 승인 이력인 `Grant`, `evaluateCreation` 진입점을 둔다. Spring Bean, Controller, Repository로 등록하지 않는다.

| 항목 | 판정 기준 |
| --- | --- |
| 승인자 | 성인 본인 확인을 한 `PATIENT` 본인. 보호자·관리자·다른 환자의 대리 승인은 거부 |
| 대상 | 지정 보호자 1명과 대상 환자 1명. 승인 시와 생성 요청 시 보호자 역할 확인 |
| 요청 범위 | 예약 전 발급한 `clientRequestId` 1건과 승인 당시 정규화된 생성 본문의 SHA-256 fingerprint. 다른 요청이나 변경된 본문에 재사용 불가 |
| 재승인 | `(환자, 보호자, clientRequestId)`별 현재 상태 한 건을 교체하며 버전 증가. 최신 상태와 후보 승인의 키·버전·ID·내용이 일치해야 생성 가능 |
| 유효기간 | 승인 시각 이상, 만료 시각 미만. 기간 값은 호출 계층이 제공하며 코드에서 운영 기간을 임의 확정하지 않음 |
| 철회 | 환자 본인만 변경하며 버전 증가. 현재 버전으로 반복 철회하면 기존 결과 유지. 철회 기록이 있으면 과거 시각으로도 새 생성 허용 불가 |
| 정책 버전 | 서버의 현재 정책 버전과 저장된 승인 버전 일치 필요 |
| 기본 거부 | 승인 없음, 현재 승인이 아닌 이력, 역할·환자·보호자·요청 ID·본문·정책 불일치, 시작 전, 만료, 철회 |

이 승인은 예약 생성에만 사용한다. 예약 수정·취소, 건강정보 조회, 채팅, 첨부, 위치, 리포트 열람이나 법정대리 관계를 허용하는 근거가 아니다. 기존 `AdultPatientGuardianSharingPolicy`와 예약별 정보 범위 검사는 별도로 유지한다.

`requestFingerprint`는 클라이언트가 보내는 권한 값이 아니다. 서버가 승인 화면에 제공한 검증·정규화 본문으로 `AppointmentCreateFingerprint.from`을 계산해 승인에 저장하고, 최초 insert 직전에도 현재 본문으로 다시 계산해야 한다. 동일 요청 ID로 병원·시각·건강·복약·이동 조건을 바꾸면 `REQUEST_CONTENT_MISMATCH`로 거부하고 환자 재승인을 요구한다. 기존 예약 insert 이후의 멱등성 검사만으로 이 사전 승인을 대체하지 않는다. 원문이나 fingerprint를 로그·공개 댓글에 기록하지 않는다.

재승인은 독립 `Grant` 추가가 아니라 기존 `ApprovalState`를 입력으로 하는 상태 전이다. 최초 승인 버전은 1이며 재승인과 철회마다 증가한다. 철회 이력도 현재 상태에 남겨 버전을 0으로 초기화하지 않는다. 상태 변경은 `expectedVersion`이 현재 버전과 다르면 거부한다. 생성 판정에는 현재 상태와 후보 이력을 **별도로** 전달하며, 후보를 최신 상태처럼 감싸서 전달하면 안 된다. 이전 승인은 `GRANT_SUPERSEDED`로 거부하고, 같은 본문 재승인·본문 A→B→A 복귀·같은 버전에서 경합한 다른 승인도 ID와 전체 값 비교로 구분한다.

순수 Java 값의 교체는 DB 원자성 구현이 아니다. 저장 계층은 요청 키별 유일한 현재 행과 별도 추가 전용 감사 이력을 두어야 한다. 초기 상태는 행이 없을 때만 만들고, 재승인·철회는 현재 행의 버전을 조건으로 갱신하거나 해당 행을 잠가야 한다. 초기화나 경합이 충돌하면 최신 상태를 재조회하고 이미 계산한 전이 결과를 덮어쓰지 않는다. 생성 판정은 같은 트랜잭션에서 잠근 현재 행을 사용해 예약 insert까지 유지해야 한다. 이 저장 계약의 구현·격리 DB 경합 검증 전에는 API를 활성화하지 않는다.

## 대안과 선택 이유

- 기존 `APPOINTMENT` 정보공유 범위로 생성까지 허용하면 읽기 동의를 쓰기 권한으로 확대하고 예약 전 승인도 표현할 수 없다.
- 보호자 역할이나 프로필 연결만으로 허용하면 환자의 명시적 승인·철회 경계가 사라진다.
- 현재 MVP 규모에서는 별도 서버를 추가하지 않고 기존 Spring 안에서 요청 1건에 대한 판정부터 검증하는 방식이 변경 범위가 작다. 다중 환자 관리 화면은 만들지 않는다.

## 다음 연결 순서

1. 환자 본인이 지정 보호자와 생성 요청을 확인하고 승인·철회하는 API 및 저장 계약을 만든다. 클라이언트가 보낸 `Grant`, 역할, 승인자, 시각, 정책 버전을 그대로 신뢰하지 않고 인증된 사용자와 서버 저장값으로 판정한다.
2. 요청 키별 현재 승인 상태와 추가 전용 감사 기록을 서버 전용 schema에 저장한다. 유일 제약, 버전 조건부 교체, 활성 계정·역할 재확인, 재승인/철회와 예약 insert의 동시성 잠금을 격리 DB에서 검증한다. 지금의 판정기만으로 중복 insert나 DB 경합을 방지했다고 보지 않는다.
3. 승인 당시 fingerprint와 현재 생성 본문을 먼저 비교하고, 기존 `clientRequestId`와 insert fingerprint로 재시도 충돌도 검사한다. 승인 검사와 insert를 같은 트랜잭션으로 묶고, 실패 시 승인 사용 상태도 rollback한다. 승인 fingerprint를 단순 본문 수정으로 교체하지 않는다. 재시도 응답 역시 최신 동의 범위 이상으로 정보를 반환하지 않는다.
4. 예약 생성과 정보공유 동의를 별도로 연결한다. 생성자가 보호자라는 이유만으로 `APPOINTMENT`, `REPORT`, `CHAT`, `ATTACHMENT` 범위를 자동 부여하지 않는다.
5. Android의 보호자 진입·환자 승인·거부 안내와 예약/리포트 조회를 연결한다. 그 뒤에만 현재 생성 403을 대체하고 DEV 종단 검증을 한다.

의사결정 능력이 제한된 환자나 법정대리인 증빙은 이 계약의 대상이 아니다. 해당 법률 검토를 성인 환자 본인 승인 개발의 전면 차단 사유로 사용하지도 않는다.

## 검증과 영향

- 정책 테스트 45건이 통과했다. 기존 32건에 현재 승인 대체, 동일 본문 재승인, A→B→A, 오래된 변경 요청, 같은 버전의 다른 승인, 후보 내용 변조, 철회 후 재승인, 시간 역전, 상태 키·버전 불일치와 오버플로 경계를 추가했다.
- 9월 27일 재승인 수정 뒤 `core-api check --rerun-tasks` 전체 451건, 실패·오류·건너뜀 0건을 확인했다. 기존 보호자 생성·수정·취소 차단 및 프로필 미조회 테스트를 유지한다. GitHub CI는 최종 PR의 커밋별 검증 기록에서 별도로 확인한다.
- Android, Firebase Rules, DB migration, 운영 권한·데이터, 배포 설정 변경 없음. 앱 실행 경로에 연결되지 않은 순수 판정 수정이므로 실기기 검증은 해당하지 않는다.
- 관리자 웹 영향: 현 단계에는 API·DB 계약 변화가 없다. 저장 계약을 추가할 때 신청자와 환자 구분, 생성 승인과 정보공유의 차이를 공유 계약에 반영한다.

리스크는 판정기를 너무 일찍 실제 API에 연결하는 것이다. DB 잠금·감사·환자 승인 화면 없이 활성화하거나 클라이언트 제공 승인 객체를 신뢰하면 안 된다. 이 문서와 코드 준비를 #419 전체 완료나 운영 승인으로 표시하지 않는다.
